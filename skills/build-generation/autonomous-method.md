# 자율 설계 실행 계약

source_policy가 pok-primary이면 **PoK 설계·웹 검증 방법**이다. 탐색·앵커 선택은
PoK의 게임 사실·관계·메커니즘 인사이트와 에이전트 판단으로 한다. 전체 Build/
UsageProfile·서술형 빌드 문서와 다른 사용자의 빌드/가이드는 정보원에서 제외된다.
일반 웹검색은 노출되지 않는다. 웹은2단계 이후 workflow_primary_source로 **이미
선택·기록한 claim의 provider**를 확인하는 원문 조회만 한다. 먼저 PoK 카탈로그 근거와
구체 provider를 기록한다. 이 도구는 추천·관련 목록·커뮤니티 탭을 제거한 데이터
페이지와 실제 읽기 receipt를 준다. 원문에 없는 연결을 도구가 검증한 것처럼 쓰지 않는다.
조회 실패는 기재 부정/수집 누락/실험 확인과 다르다. 원문으로 확인하지 못한 핵심
연결은 기존 실험 가정 승인 절차를 따른다. 임의 외부 URL을 근거로 만들지 않는다.

이 모드에서 workflow_context는 작은 실행 문맥만 준다. workflow_contract에서 필요한
edits/flow/planning 계약만 읽고, 편집 연산과 record 스키마를 혼동하지 않는다.
extensions 저장은 {op:merge_extensions,value:{확장명:객체}}다. 저장 후 반환 record_ref를
이어 쓰고, 전체 record_json을 재회수하지 않는다. 현재 재료는 workflow_read_record의
material 투영으로 확인한다. 저장·측정 부착의 작은 반환은 정본 내용을 바꾸지 않는다.

재개 시에는 `workflow_read_record`의 flow와 필요한 decisions/evidence/questions ID만
읽어 현재 정본에서 이어갈 수 있다. 전체 record_json 문자열을 다시 페이지 조회할
필요는 없다. 복구 알림이 있으면 이미 저장한 설계를 재탐색하지 말고 누락 검사와 현재
단계 제출부터 마친다. 내용 판단이 실제로 끝나지 않았다면 미완료를 명시한다.

가정 사용 승인 사실은 호스트의 human_replies/approved_hypotheses 원장에 보존한다.
이를 게임 사실을 입증한 새 카탈로그 근거나 인게임 관측으로 바꾸지 않는다. 문장 보강과
비용 계산만으로 같은 승인을 다시 요구하지 않으며, 실제 주장·공급자·의존·근거가
바뀌면 승인의 적용 범위를 다시 확인한다.

사용자의 원문 요구와 고정 조건을 보존한다. 운영자가 후보 답안을 주지 않는다.
호스트가 user.request에 저장한 원문만 사용자 고정의 출처다. 에이전트는 user_fixed를
만들거나 원문 결정을 수정하지 않는다. 요구의 해석·전직 배분·장비·링크·수치 목표는
다른 역할의 결정으로 기록해 필요하면 바꾸고 원문 요구와의 관계를 설명한다.
판단과 조사는 에이전트가 수행한다. 단계는 산출물·재개 관문이지 도구 호출 횟수나
후보 개수 할당량이 아니다. 단계 안에서 자유롭게 조사하고 모순이 나오면 이전 선택을
수정한다. 예산 안에서 끝내지 못하면 부족을 숨기지 말고 incomplete로 제출한다.

처음 workflow_context, server_info, get_server_capabilities로 현재 실행과 도구를
확인한다. context의 record_ref에서 이어가되 workflow_read_record의 흐름·결정 인덱스와
필요한 ID만 읽는다. 봉인된 JSON 원문 전체 재독을 기본 경로로 삼지 않는다.
get_design_record_schema로 기존 계약을 확인한다. update_design_record로 같은 기록을 개정하고 최종 반환
record_ref를 응답에 넣는다. design.md는 정본 기록에서 생성된다. 원문 전체가 필요한
도구 결과만 get_tool_result로 선택 회수하고 동일 결과 전체를 반복 조회하지 않는다.
긴 설계도 한 번의 원자적 변경에 전부 넣을 필요가 없다. 근거·결정 묶음을 나눠 저장한다.

## 1. 메커니즘 탐색

현재 단계에서 필요한 것은 잠정 주안·핵심 작동 연결·대안과 대가다. 모든 장비 접사,
완성 트리, 전체 치명타 수치와 회복 시뮬레이션까지 끝내느라 이 단계 제출을 미루지
않는다. 주안은 뒤 단계의 근거로 바뀔 수 있다. 형식 채우기보다 실제 판단을 기록한다.

PoK 검색·상세 원문·인사이트부터 확인한다. 필요에 따라 공급·상태 그래프, 스케일러,
적대·성립기 도구를 쓴다. 공격 한 번의 효과뿐 아니라 시작→반복→중단→다음 팩 재시동,
처치 없는 보스전과 성장 경로·슬롯/조작 대가를 비교한다. 스킬이나 장비의 이름만
나열하지 않는다. 후보별 결정과 기각/보류 이유를 기록한다. 주안은 변경 가능하다.

## 2. 성립 검토

선택한 핵심 연결의 성립/반례/미확인을 검토한다. 모든 강화 후보의 최종 우열이나
완성 장비 수치를 이 단계의 종료 조건으로 삼지 않는다.

아이템 부위는 이름 토큰 대신 category/sub_type으로 확인하고 효과 검색은 영문 원문도
사용한다. 조회0건의 진단을 먼저 읽는다. 수치는 find_by_value로 확인한다. 스태킹은
공급·보상 사슬과 상태 연계를 추적하고 증가/증폭·상한·주체·실제 획득 가능성을 구분한다.
담체 개수나 툴 추천 순서를 배율/우열로 읽지 않는다. 고정 핵심 기재는 서술/인사이트의
확인된 제약까지 읽는다. 키스톤·피해 타입 금지와 다른 공급자의 적대도 확인한다.

PoK 조사 다음 웹에서 핵심 기재 사이의 실제 연결을 조사한다. 부품 각각의 존재로
연계를 입증하지 않는다. 출처 버전·검증 대상·예외·한계를 명시한다. 핵심 연결마다
별도 결정으로 만들고 catalog/external 근거를 연결한다. catalog 근거는
workflow_catalog_source 도구가 내는 실제 record_sha256과 field_path를 이용한다.
웹 근거는 실제 읽은 URL과 연결을 지지하는 내용·범위를 rationale에 적는다.
도구가 문장 해석의 진실성을 인증하는 것은 아니다.

웹에서도 확인하지 못한 핵심 연결은 hypothesis로 유지하고 질문을 기록한 뒤
needs_user로 제출한다. 질문에는 정확한 가정·확인된 부분·실패 영향·진행 대안을
적는다. 사용자가 승인한 claim ID와 지문만 가정 사용을 허용한다. 승인 후 이를
source_supported나 인게임 확인으로 바꾸지 않는다. 새 가정과 물리적 제약은 승인에
포함되지 않는다. 거절되면 다른 메커니즘을 탐색하고 앵커를 다시 검토한다.

## 3. 상세 앵커 설정

추상적인 필요조건만으로 완료하지 않는다. 각 앵커는 기존 decision 필드로 작성한다.

- 역할: user_fixed / mechanism_required / provisional / power_candidate.
- 정확한 공급자: KB entity_id, 이름, 부위·스킬 링크·패시브 노드 위치/ID.
  필수 고유 아이템이면 어느 옵션이 필수인지, 일반 장비면 필수 베이스/접사 조건과
  필요한 수치를 적는다. 보조젬도 정확한 등급/종류·연결 대상·효과·대가를 적는다.
- rationale: 효과→다음 기재→빌드 성립 또는 이득의 인과, 선택·기각 이유.
- depends_on: 선행 앵커와 실제 공급자. alternatives: 대체 결정과 손익.
- costs: 슬롯·포인트·점유·능력치·마나·조작·기회비용. 수치 미측정은 null과 이유.
- evidence_ids, limitations, review_triggers: 근거와 미확인·재선정 조건.

공격·방어·자원/회복을 모두 구체화한다. DPS/EHP/사용감 개선 앵커도 실제 후보로
기록하되 필수로 승격하지 않는다. 장비·주얼·스킬·보조·패시브의 검토를 빠뜨리지
않는다. 필요 없는 부류는 이유를 기록하고 억지로 채우지 않는다. 고가치 고유·혈통
보조·특수 주얼은 해당 빌드의 효과와 기회비용으로 검토한다. 희귀 장비만 먼저 채운
다음 남은 칸에 고유를 붙이는 접근을 피한다. 특정 상품 개수는 성공 기준이 아니다.

장비 완성도는 `check_item_legality.affix_inventory`의 실제 모드 ID·사용량/한도로
확인할 수 있고 계산·조립도 슬롯별 요약을 반환한다. 매칭이 불완전하면 전체 접사
수로 읽지 않는다. 남는 용량·찬 접사 수만으로 적합성이나 종결 성능을 판정하지 않는다.

예산 미정은 저예산이나 고유 미보유를 뜻하지 않는다. 희귀 장비의 가상 목표 접사는
허용하면서 고유/주얼만 실물 보유를 요구하는 비대칭을 만들지 않는다. 실제 존재하는
변형·범위·획득 가정을 확인한 고가치 조합은 현재 구현으로 채택할 수 있다. PoB의
미측정/미파싱은 효과0이나 영구 보류의 근거가 아니다. 예상 효과가 목적에 직접 기여하고
대가를 감당하면 필수 구현/잠정 채택으로 올리고, 숫자 측정이 남았다는 사실을 따로 적는다.
동시에 사용할 수 없는 옵션과 자료가 실제로 부족한 변형은 구분한다.

### 자원·치명타·고가치 조합 판단 검토

자연 재생 완전 충당을 보편 성립 조건으로 만들지 않는다. 맵핑·처치 없는 보스·
중단 후 재시동을 나누고 재생, 플라스크, 흡수, 명중/처치 회복, 비축량, 소모 변경의
공급·가용 조건·기회비용을 비교한다. 보스에서 처치 회복이 꺼진다고 플라스크까지
배제하거나 무한 지속을 모든 전투의 기본값으로 두지 않는다. 유한 플라스크는 시작 충전,
사용당 회복/비용·지속시간·추가 충전원·소진 후 대응을 기록한다. 전투 시간이 미정이면
가정한 공급과 소모에서 버틸 수 있는 시간을 역산하고 불명확을 남긴다. 맵핑 처치 회복을
보스 상시 공급으로 복사하지 않는다. 비용 보조·회복 접사·회복 이동 노드와 피해 보조·
공격 접사·플라스크 사용의 완성 조합을 비교한다. 자연 회복만 맞추려고 피해 슬롯을
먼저 포기하거나 반대로 회복이 공짜라고 가정하지 않는다.

명중형 피해에는 치명타 확률·피해 배율·명중률·조건 유지와 비치명타 대안을 검토한다.
치확 투자가 어렵다는 이유만으로 비치명타로 끝내지 말고 기본 치확 변경·보장 치명타·
조건부 성립기 등 다른 공급 경로를 조사한다. 조건부 효과의 대상/주체·이동/피격·
유효 시간과 준비 비용을 확인한다. 비치명타가 더 적합하면 선택 이유와 포기한 성장성을
기록한다. 고가치 고유·혈통 보조·특수 주얼은 피해·방어·자원·사용감을 함께 바꾸는
묶음으로 평가하고, 필요한 링크/패시브/접사도 함께 재선정한다.

선택한 투자의 다른 활용처도 조사한다. 사용자가 지정한 스태킹 축만 반복 검색하지
말고, 이미 투자하려는 능력치·퀄리티·레벨·범위·주얼 효과·지속 상태가 다른 스킬,
보조, 방어, 자원 공급자에서 무엇으로 바뀌는지 공급/상태/스케일러와 원문으로 추적한다.
조회된 담체 수를 강함으로 보지 않고, 그 투자로 새로 열리는 연결과 상한·주체를 본다.
유니크/주얼의 고정 템플릿이 전부라고 단정하지 않는다. get_entry의 variant_context가
있으면 필요에 따라 get_variant_pool로 변이 효과를 탐색하고 상세 원문/웹에서 해당
아이템의 실제 변형을 확인한다. 공용 풀에 있다는 이유로 그 아이템에 붙는다고 가정하거나
교체 전후 옵션을 모두 합하지 않는다. 미확인 핵심 연결은 기존 실험 승인 절차를 따른다.

단일 슬롯의 승자만 모아 묶음을 끝내지 않는다. 선택한 기재의 효과를 바꾸는 다른
공급자나 증폭기를 찾았으면 함께 필요한 스킬·보조·패시브·장비·주얼·회복 수단을
교체한 조합으로 비교한다. 같은 기능의 대안인지, 성능도 비슷한지는 구분한다.
강한 후보를 보류했다면 현재 조합을 유지할 이득과 재검토 조건을 기록한다. 후보 수나
특정 아이템의 채택 개수는 목표가 아니다. 비교가 실제로 끝나지 않았으면 미완료로 남긴다.

review_policy가 planning-v2이면 extensions.planning_reviews에 workflow_context의
스키마대로 장면별 자원 계획, 회복 대안, 치명타 선택, 고가치 묶음 판단의 결정 ID와
근거를 연결한다. 검사는 검토 누락·참조를 확인할 뿐 특정 선택이나 성능을 인증하지 않는다.
workflow_context와 자체 workflow 도구의 남은 시간 표시를 확인해 저장·최종 제출 여유를
남긴다. 최종 저장 뒤 이미 읽은 원장을 전부 다시 읽느라 제출 상한을 넘기지 않는다.

패시브는 노드 이름과 효과, 필수/선택, 연결 비용의 추정/실측, 전직 전용/해금과
서로 경쟁하는 앵커를 기록한다. 전체 트리·PoB를 만들기 전에는 총포인트 적법성을
확인했다고 말하지 않는다. 점유·속성·중복 고유·슬롯·보조 적합성·상태이상 금지·
무처치 자원 순환·상시가 아닌 버프를 검토한다. 실제 성립이 불분명하면 필요한
공급자를 더 조사하거나 구현을 변경한다. 계산/최적화 미완료와 구조적 불가능을 구분한다.

3단계에서 남은 포인트를 전부 쓰거나 완성 트리를 최적화할 필요는 없다. 필수/현재안
앵커의 접근 비용·알려진 배타·슬롯·요구치에 대략적인 성립 근거가 있으면 estimated로
표시하고 실제 경유 속성 선택·전체 잔여 배분·공격/방어 최적화는 extensions의
assembly_tasks에 anchor_ids, 필요한 계산, 통과 조건을 적어4단계로 넘긴다. 알려진
포인트 초과나 공급자 부재를 estimated로 숨기지는 않는다. 전체 배분을 안 했다는
이유만으로 이미 선택한 앵커까지 미정으로 되돌리지 않는다.4단계에서는 이 미완료를
실제 조립·계산으로 해결하고 실패한 앵커의 대안을 재비교한다.

extensions.autonomous_flow는 workflow_context의 스키마를 따른다. core_link_ids는
핵심 연결 결정, anchor_ids는 상세 앵커 결정, selected_mechanism_id는 현재 주안이다.
component_review와 budget_review는 누락 검사용 참조와 판단 근거이며 빌드 정본을
복제하지 않는다. 앞 단계에는 아직 앵커·예산 검토가 없으면 빈 배열을 쓸 수 있다.

## 4. 앵커 기반 초안

희귀 아이템의 Prefix/Suffix 선언 명세와 실제 계산용 문구를 구분한다. 계산에는
렌더된 text를 쓰고, spec_text만 얻었다면 실제 아이템으로 렌더한 뒤 사용한다. 선언이
적법하다는 것만으로 접사가 계산된다고 가정하지 않는다. 공급자 결박의 해시를 추측하지
말고, XML 재료라면 inspect_pob_document가 반환하는 실제 pointer와
provider_binding_value_sha256을 사용한다. 재료가 바뀌면 해당 결박과 측정도 재검토한다.

아이템 부여 인스턴스와 같은 이름의 일반 젬 인스턴스는 구분한다. 목걸이 베이스가
부여한 스킬의 무료 점유처럼 KB/사용자가 확인한 사실과 PoB의 알려진 점유 결함을
혼동해 가짜 부족을 맞추려고 빌드를 약화하지 않는다. 실제 다른 점유 부족까지 면제하는
것은 아니며, 출처·부여원과 원시 계산/조정 근거를 함께 표시한다.

검토 관문과 승인이 허용할 때만 수행한다. build-assembly 절차와 같은 설계 기록을
이어받고 구체적인 스펙/PoB 재료를 연결한다. 앵커의 실제 부착·요구 수치·포인트·
점유·적법성·계산 범위·config 유지 조건을 검증한다. 불가능한 묶음은 대안을 비교해
선택을 재개방한다. 근거 없는 user_fixed 변경은 사용자에게 묻는다.

## 5. 초안 비판·피드백 개선

표기 DPS만으로 완료하지 않는다. 빈 주얼·죽은 패시브·무효 보조·부족한 회복·
과도한 준비/조작·조건부 버프·희귀/고유 조합 기회비용을 비판하고 필요하면 조합을
변경·재측정한다. 초안과 변경 이유·득실·실제 근거를 제공하고 사용자 피드백을
기다린다. 피드백이 들어오면 같은 기록에서 해당 선택과 의존 앵커를 재검토한다.
비판 결과는 extensions.autonomous_critique의 findings와 response에 기록한다.

응답의 ready는 해당 단계 산출물을 제출했다는 뜻이며 좋은 빌드 인증이 아니다.
모든 보고는 한국어로 작성한다. 공개 설계 근거만 저장하며 숨은 추론 전문은 요구하지 않는다.
