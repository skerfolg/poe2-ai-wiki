# 핵심 조합 탐색

이 단계의 산출물은 조립에 넘길 설계 초안이다. 사용자의 원래 목표와 고정 조건을
판단 기준으로 삼는다. 새 생명력·EHP·DPS 바닥선이나 특정 방어 구조를 임의로
필수 조건으로 만들지 않는다. 수치로 환산되지 않은 이동·응답성·조작·자원 여유도
그것이 목표에 기여하는 경로와 대가로 비교한다.

1단계에서는 입력 → 효과 → 다음 공격·이동으로 이어지는 작동 경로와 병목을
설명하고 구조가 다른 구성 묶음을 제시한다. 부품 하나의 단독 수치가 낮다는
이유로 그 부품을 필요로 하는 묶음을 제거하지 않는다. 이미 제공된 레코드의
필드 목록과 원문을 확인한 뒤, 결정을 바꿀 미해결 질문에 조회 예산을 배분한다.
`granted_instance` 같은 부여 인스턴스 정보와 인게임 확인 기록도 소비한다.
관련 durable 인사이트는 `search_insights`로 확인하고 필요한 전문을 읽는다.

검색 결과의 이름·ID를 얻는 일과 효과 본문을 읽는 일은 다르다. 이름을 아직
모르는 핵심 규칙을 확인할 때는 제공된 `search_and_read`로 검색과 상세 읽기를
연결할 수 있다. 범위·필드는 직접 선택한다. 첫 검색 결과가 가장 좋은 빌드
부품이라는 뜻은 아니며, 선택 범위 밖의 결과도 미열람으로 남는다. 검색 1회와
상세 N회는 실제 조회 1+N회를 소비한다. 이미 ID와 필요한 필드를 알면
`get_entry`로 바로 조회한다. 재확인이 필요하면 이유를 남긴다.

2단계에서는 반환된 원문으로 각 묶음의 결정적인 연결을 확인한다. 자료 부족,
자료와의 모순, 실제 작동 확인을 구분한다. 핵심 연결이 불명확하면 그 연결을
가르는 질문을 먼저 해결한다. 도구가 계산하지 못한다는 이유만으로 이득을 0으로
취급하지 않는다. 새 조합을 만들거나 기존 구성요소를 바꾸면 어떤 가정과 근거를
그대로 쓸 수 있고 무엇을 다시 확인해야 하는지 공개 판단에 적는다.

3단계에서는 원래 플레이 목표에 돌아가 잠정 주안과 가장 중요한 구조 대안을
비교한다. 단일 점수·이름·목록 길이로 선택하지 않는다. 선택이 뒤집히는 조건,
준비 상태와 반복 상태, 처치 없이 가능한 순환, 입력·슬롯·획득 대가를 연결한다.
마지막에 처음 도입한 연결은 이미 검증된 연결로 승격하지 않는다. 모든 후보가
현재 조건을 충족하지 못하면 선택을 비워도 된다. 후보의 보류·기각 사유와
구성 변경 이력은 보존한다.

확정된 사실, 잠정 설계, 미검증 연결, 다음에 수행할 가장 작은 검증을 구분해
보고한다. 공개 판단과 근거만 작성한다. 이 초안은 `design.md`와
`build_spec.optimization_contract` 작성의 입력이며, 완성 빌드·최적화 완료·
`assemble_pob` 추천 관문 통과를 의미하지 않는다.
