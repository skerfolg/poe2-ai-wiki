# build-generation — 빌드 생성 워크플로 (BLUEPRINT §10.0 설계 루프 + §10.2 파이프라인)

> **상태**: P4.5 개정 (2026-08-02) — 중심을 **설계 루프(제약 충족 + 가설 관리, D25)**로 재정의. P3 파이프라인(아래 5~8)은 루프 5~6단계의 실행 뷰로 유지.
> 도구는 pok MCP: 설계 루프(`parse_design_doc`·`check_constraints`·`evaluate_objective`·`parse_pob`) + 조회(`search_kb`·`get_entry`·`related`) + 계산(`compute_pob`·`evaluate_delta`·`check_item_legality`·`assemble_pob`).
> **역할 분담**: 판단·창의는 이 스킬을 실행하는 에이전트, 산수·검증·기록은 엔진. **PoB는 계기(instrument)** — 효율을 추측하지 말고 측정해 읽는다(AD-8).

## 설계 루프 (상위 계층, D25 — 7단계)

**design.md가 1급 산출물이다**(D26): PoB 코드는 상태의 스냅샷, 설계 문서는 판단·제약·가설의 기록. 규격은 [BUILD_DESIGN.md](../../docs/BUILD_DESIGN.md) — 세션을 이어받으면 **가장 먼저 `parse_design_doc`로 기존 문서의 `상태:` 줄과 검증 큐를 읽는다**.

1. **빌드 컨셉 정하기** — 고정 조건(협상 불가)·설계 철학을 문서 상단에 명시.
2. **수행 가능성 검토** — KB 조회 + 앵커(`parse_pob`, `artifacts/anchors/`) 대조.
   고정 조건의 핵심 엔티티(어센던시 노드·키스톤·핵심 유니크)는
   **`get_entry(include_narrative=True)`로 서술(판단 노트·인게임 확인 기록)까지 소비**한다 —
   KB에 축적된 인사이트는 읽는 경로가 있어야 다음 생성에 반영된다.
3. **최적 직업군·어센던시 파악**.
4. **최소 구동 조건 확인 = 성립 질문** — 고정 조건의 각 메커니즘마다 "부작용·비용은
   무엇이며 현재 상태가 버티는가"를 묻고, 원본·경감·가용 자원이 수치로 있으면
   `check_constraints`의 sustain(지속 가능성 경계)으로 **측정 전에 상·하한부터 계산**한다.
   경계에서 나온 필요 경감·필요 자원은 요구-수급 장부로 (BUILD_DESIGN §2-3 성립 질문 규율).
5. **필수 어센던시·패시브·아이템 확정** — 아래 파이프라인 5~6 + 트리 최적화 도구.
6. **스킬 리스트업·보조젬 매칭**.
7. **지속 반복** — 문제 수정·새 가능성 발견이 ①~⑥으로 되먹임. 버전을 올리고 `상태:` 줄을 다시 쓴다(갱신 규약 §3).

**매 반복에서 제약 원장을 기계 검증한다(D27)**: 문서의 표·수식을 `check_constraints` 입력으로 전사 —
포인트 예산(배타 분기 열거)·색상 장부(과반+여유분)·점유 산수(로우라이프 경계+효율 상한)·자원 소진(성유·슬롯).
위반이면 설계를 고치고, 여유분(headroom)은 문서에 기록한다. "대충 된다" 금지 — 재계산 가능해야 한다.

**목적은 임계·캡의 사전식 판정이다(D28)**: 목표 상태를 `evaluate_objective`의 targets(우선순위 순)로 적고,
실측값(PoB stats·인게임 정보창·검사기 리포트)만 넣는다. 첫 미충족 = 다음 병목 — 그것부터 푼다.
미측정 지표는 충족이 아니라 **측정 큐**다.

**가설은 3구분으로 관리한다(D29)**: 확정/잠정/미검증. 미검증 상호작용은 공격 배율·방어 계산에
선반영 금지. 미검증 목록 + 검증 항목 큐가 다음 세션·인게임 플레이의 작업 목록이며 P5 피드백 입력이다.

## 파이프라인 (루프 5~6단계의 실행 뷰, §10.2)

1. **요구 분석**: 컨셉·제약·목표를 자연어로 받아 **목표 상태(임계·캡) + 다차원 프로파일**로 옮긴다
   (RC3 — 단일 축 금지, D28 — 평평한 가중 합산 금지): 공격(지속/폭발·단일/광역)·방어(EHP·회복·최대피격)·속도·
   클리어(이동·공/시전속도·AoE)·일관성(자원·명중·조건충족)·QoL 중 콘텐츠 목표별 경계.
2. **KB 조회**: `search_kb`(게임 용어) → `get_entry`(fields 선별) → `related`(관계 순회).
   시너지는 키워드가 아니라 **관계 그래프**(`scales_with`·`triggers`…)로 판단(RC2).
   조건(condition)은 만족 가능성까지 확인 — 발동 가정 금지(RC1).
   메커니즘 규칙·공식·한도는 `type=Mechanic` 레코드(점유 효율·전직 예산·보조 한도 등)를 인용.
3. **후보 초안 2~3개**: 스펙 수준(클래스·어센던시·핵심 스킬·키스톤·아이템 방향)으로만.
   앵커는 검증된 패턴(추천 모드 — `artifacts/anchors/`의 계보 있는 빌드) 또는 KB 패턴+사용자 컨셉(발명 모드) — 사용자가 정한다.
4. **사용자 선택/피드백 대기**. 수정 요청이면 3으로.
5. **선택안만 3티어(저/중/고) 조립** (D18 — 레벨 동일, 레어 어픽스 품질·유니크
   의존·트리 완성도 차이):
   - 합성 아이템은 먼저 `check_item_legality` — ILLEGAL/UNKNOWN이면 그 모드를 쓰지
     말고 대체(우회 금지). CONDITIONAL은 획득 경로를 티어 산정(비용)에 반영.
   - 트리 노드는 KB `node_id` 그대로. **시작점과 연결된 경로**여야 한다 —
     `compute_pob`의 `pruned_nodes`가 비어있지 않으면 비연결이니 경로를 고쳐라.
   - `assemble_pob(spec, slug)` — slug는 한 줄 요약(예: `spark-stormweaver-저티어`).
6. **자체 검증**: 반환된 실측 스탯을 1의 프로파일과 비교. **validation은 floor일 뿐
   목표가 아니다**(RC1) — 저항 캡·EHP 하한 등 바닥선 미달이면 5로 돌아가되,
   무엇을 바꿀지는 `evaluate_delta`로 **후보 변경안들을 실측 비교**해 고른다.
7. **전달**: `build_code`(PoB 붙여넣기), 티어별 스탯 요약, 트레이드오프 설명,
   인게임 테스트 요청. 가격 추산은 **사용자가 요청할 때만**(D19).
   **design.md도 함께 갱신**한다 — 버전·상태 줄·3구분·검증 큐 (BUILD_DESIGN §3).
8. **피드백**: 인게임 결과는 design.md의 미검증 목록에 대조해 기록 —
   확정 승격은 인게임 확인·PoB 실측 근거가 있을 때만(§2-5). 큐레이션은 P5 구현 대기.

## 금지 사항

- ⛔ 노드/아이템/모드의 효율 **추측 서술** — 반드시 `evaluate_delta` 실측 인용.
- ⛔ 제약 원장 없이 링크·전직·점유 변경 — 변경마다 `check_constraints` 재계산
  (보조 하나 추가가 색상 분모·점유·발동 계산을 동시에 바꾼다, v6 실증).
- ⛔ 미검증 가설의 계산 선반영 — 3구분(D29)에서 확정으로 승격된 것만 배율에 넣는다.
- ⛔ **수급안 없는 요구 수치** — 계산식·목표·예시에 인용한 요구 수치는 `search_kb`로
  소스를 열거한 수급 장부 없이 확정·잠정 채택 금지 (BUILD_DESIGN §2-3 요구-수급 규율,
  "기본값 → 요구값" 간극 명시 포함). 가격 추산은 여전히 요청 시만(D19) —
  수급 *경로*의 존재·희소성까지만 장부에 적는다.
- ⛔ **가정 수치 미등재** — **본문 서술·수식·예시 어디에 있든** 기본값·캡을 넘는 인용
  수치는 목표 상태로 등재 후 장부화한다. "가능하면/높은" 같은 수식어 목표는 수치화한다.
  **빌드 성립 조건**(미충족 시 운용 불가)은 사전식 목표 최상위군에 — 성립 조건 미해결
  상태에서 하위 목표 최적화 금지 (BUILD_DESIGN §2-3 가정 수치 등재 의무).
- ⛔ **경계 미계산 측정 도피** — 부작용·비용의 원본·경감·가용이 수치로 있는 항목을
  경계 계산(sustain) 없이 측정 큐로만 미루기 금지 — "미측정"과 "경계 계산 가능"은
  다르다 (BUILD_DESIGN §2-3 성립 질문 규율).
- ⛔ **한 축 점유 장부로 전체 대신하기** — 점유 검사는 자원 축마다(생명력·정신력 등) 각각
  장부를 만든다. 지속 스킬·보조의 점유는 KB 수치(reservation·additional_reservation)로
  전수 합산 (BUILD_DESIGN §2-3 축별 점유 장부).
- ⛔ **실측 이상 신호의 무반증 처리** — 초과·음수·기대 불일치를 "모델링 인공물"로
  결론 내리기 전에 반증(해당 요소 제거 재실측 등)을 기록한다 (BUILD_DESIGN §2-3).
- ⛔ **미매칭을 KB 갭으로 단정** — `check_item_legality`의 UNKNOWN·검색 0건은 조회 실패
  신호다. 도구가 제시하는 **표기 확인 후보**를 먼저 보고, 정본 표기·영문명으로 재조회한
  뒤에야 갭으로 기록한다 (BUILD_DESIGN §2-3 조회 실패의 원인 규명 의무).
- ⛔ **루프 밖 설계 문서 수동 편집** — design.md는 설계 루프 실행의 출력물로만 갱신
  (BUILD_DESIGN §3-0). 도메인 지식·피드백은 KB·규칙으로 진입시키고 루프가 반영한다.
- ⛔ 조건부 효과의 발동 가정 — PoB `config`에 정직하게 설정하고 그 결과를 읽는다.
- ⛔ `check_item_legality` 실패 모드의 우회 사용(strict 해제 등) — 대체 모드를 찾는다.
- ⛔ 후보 전부를 PoB로 심화 — **선택안 하나만** 조립·검증(계산 비용, §10.2).

## 주얼 선택 지침 (사용자 확립 2026-07-31)

- **소켓 가치는 "가정 주얼"과 함께 실측**한다 — 빈 소켓은 델타 0이라 옵티마이저가
  저평가한다. 템플릿 주얼은 빌드 컨셉에서 도출하고, 조달 가정임을 기록에 남긴다.
- **희귀 주얼 템플릿은 컨셉 의존**. 예: 주문 치명타 빌드(경계 감개)는
  `[접두] 주문 피해 증가 · 접미어 효과 % 증가 / [접미] 주문 치명타 확률 % ·
  주문 치명타 피해 배율 % · (무접두) 치명타 피해 배율 %` 5줄
  (0.5 시즌 한정 3접미/2접두 — crafting-rules season_override 참조).
  ⚠️ **"공격" 키워드 피해는 무도 무기(활·육척봉·철퇴 등) 전용** — 주문 빌드에
  넣지 말 것. 무접두("주문"/"공격" 없음) 치명타 줄은 범용(사용자 정정 2026-07-31).
  **접미어 효과 접두가 있으면 접미 수치는 최종 표시값(티어x배율)으로 합성한다 —
  PoB는 효과 줄을 계산하지 않으므로 선반영이 정직한 모델링**(실측 2026-07-31:
  효과 줄 유무 DPS 동일 51,792.2 / 접미 1.6배 수동 반영 59,000.7).
  **위는 예시일 뿐 — 케이스 하드코딩 금지**: 템플릿은 빌드의 피해 원천(주문/무도)과
  정책에서 그때그때 도출하며, 공격 빌드는 공격 치명타 줄과 무접두 치명타 줄을
  섞는 등 키워드 줄+범용 줄 혼합이 일반 원칙이다.
- **고유 주얼은 종류별 채택 전략이 다르다** (KB 13종 수록, 사용자 해설 2026-07-31):
  - 믿음의 분광기(Prism of Belief): 랜덤 젬 +1~3레벨 — 주력기 대상일 때만 가치.
    **무기 부여 스킬(예: 경계 감개의 볼트)에는 적용 불가**.
    사용 규칙: 대상 스킬명을 실명으로 넣어 `check_item_legality`로 검증한다 —
    실존 젬(KB Skill ∩ PoB prism 풀)만 통과하며 무기 부여(fromItem) 스킬은 거부된다.
  - 과대망상(Megalomaniac): 랜덤 노터블 할당 — 조합 복권형, 특정 조합 실측 필요.
    "Allocates <노터블명>" 2~3줄 실명 표기 — 적법성은 실존 recipe 노터블 대조로
    CONDITIONAL(랜덤 롤 조달 가정 — 트레이드 전제)을 기록에 남긴다.
  - 우물의 심장(Heart of the Well): 훼손 옵션(접두 2·접미 2) 선택 — 조합에 따라
    게인·치명타 옵션 구성 가능. 풀은 KB `origins: heart-of-the-well`(ModVeiled
    UniqueHeart* 수록분) — 선택지를 정책에 맞게 구성해 실측.
  - 오래된(Time-Lost) 계열: **반경 내 소형/주요 패시브에 속성 부여** — 고점 필수.
    소켓 위치(반경에 걸리는 노드들)에 따라 가치가 달라져 소켓별 실측 필요.
  - 제어된 변형·허무의 산물: **비연결 패시브 할당** — 연결 비용을 우회하므로
    Time-Lost와 연계 시 시너지. 트리 최적화의 연결 전제를 바꾸는 특수 케이스.
  - 위 특성상 고유 주얼은 단일 템플릿이 아니라 **주얼별 전략 모듈**이 필요하다.
