# build-assembly — 조립 정본 루프 (비교 후보와 최종 채택안)

> **대상**: 저비용 에이전트로도 실행되도록 **재량을 제거한 절차**. 순서를 벗어나지 말 것.
> 전제: [공통 실행 환경](../AGENTS.md#명령-실행-환경-windows--macos) 준비, `luajit` 사용 가능.
> 발의: 사용자 2026-08-09 (백로그 제안 E). 근거 사고: 백로그 #27.

## 왜 이 루프인가 — 정본이 없으면 표류한다

사용자 판정(2026-08-09): *"compute 스킬은 간단한 계산이나 초기 빌드 선정 과정의 대략적
예측에만 쓰는 게 좋겠다. 빌드 컨셉 확정 후 본격적으로 만드는 과정에는 적합하지 않다."*

실측 사고(#27): 장비를 **세션 메모리에 들고** `compute_pob`으로 20여 회 반복한 결과
**10슬롯 중 4개가 실재하지 않는 장비**였다(존재하지 않는 베이스 `Silk Gloves` · 실재하지
않는 문구 · 순수 ES 베이스에 안 붙는 접사). 그 위에서 나온 `IgniteDPS 66,702`가 설계
판단의 근거로 쓰였다. 파일로 옮겨 `assemble_pob`에 넘기자 **첫 실행에서** 전부 드러났다.

**문제는 세션의 부주의가 아니라 정본이 없는 것이다.** 기억으로 든 장비는 반복될수록
원본에서 멀어지는데, 멀어졌다는 사실을 아무도 모른다.

## 설계와 조립의 역할

| 단계 | 도구 | 성질 |
|---|---|---|
| **컨셉 탐색·전체 구성 비교** | `compute_pob`·`evaluate_delta`·`optimize_*` | 선택 근거. 누락·실패와 자원·실사용 목표를 함께 확인 |
| **후보·최종 조립** | `assemble_pob` → `artifacts/builds/<id>/` | 적법성 전량 검사, **파일이 진실**. 후보별 기록을 보존 |

⚠ 탐색 단계 수치를 **최종 근거로 인용하지 말 것.** 도구가 `items_legal`로 실격을
알려 주지만(#27), 그건 "이 수치는 못 믿는다"는 신호이지 면허가 아니다.

## 절차

### 0. 계산할 후보의 구성을 확인

한 후보를 계산할 만큼 스킬·어센던시·장비·트리가 구체적이면 조립할 수 있다.
후보 간 최종 선택을 먼저 요구하지 않는다. 무엇을 바꿀지는 `build-generation`이 판단하고,
이 루프는 비교할 후보와 채택안 각각의 실제 스펙·검증 기록을 만든다.

### 1. 스펙을 만든다 (기억이 아니라 값으로)

`build_spec` dict를 세운다. 장비는 **KB에서 가져온 실제 문구**로 채운다:
- 유니크 → `optimize_items`가 반환한 실제 아이템 문구 또는 PoB 정본의 선택 변형을
  렌더한 문구. `get_entry`로 변형·롤·조건을 확인한다. `explicits`의 랜덤 옵션
  플레이스홀더를 완성 아이템 문구로 복사하지 않는다.
- 희귀 → `optimize_rare`가 낸 `text` 그대로 (⚠ `unmeasurable`을 함께 읽을 것 — 그
  조립은 PoB가 못 재는 축을 뺀 **바닥값**이다)
- 룬 → **`optimize_runes`가 낸 `text`를 그대로.** 손으로 `{rune}` 줄만 적으면 증폭이
  조용히 빠진다(3.00배 차이, 백로그 #33)

### 2. 조립한다

```
assemble_pob(build_spec=..., slug="<빌드 이름>", purpose="exploration")
```

비교·수정 중에는 위 탐색 목적을 쓴다. **최종 추천을 출고할 때는
`purpose="recommendation"`으로 다시 조립한다.** 이 호출은
`build_spec.optimization_contract`의 요구 범위·설정·종료 기준과 생산자가 기록한
실제 증거를 검사하며, 부족하면 계산·저장 전에 거부한다. 계약은 이번 사용자 요청에
맞춰 설계 때 정한다. 호출 도장 하나나 슬롯 몇 개의 비교를 전체 최적화로 바꾸지 않는다.

현재 구성의 대안 재검토는 `evaluate_delta(..., review_component="items"|"jewels"|
"tree"|"supports"|"ascendancy")`를 쓴다. 반환 `derived_from`은 **기준 스펙**에만
연결한다. 대안을 채택했으면 새 기준으로 다시 평가한다. 실제 입력 차이·성공 측정에서
범위가 만들어지므로, 출처나 재검증 경로를 수동으로 만들어 낡은 기록을 지우지 않는다.
여러 영역을 함께 재배분했다면 단일 인자 대신
`review_components=["items", "tree", "jewels", "supports"]` 중 실제 비교 영역을 쓴다.
한 번 계산한 패키지의 결과를 영역별 실제 변경 범위에 연결하며, 변경 없는 영역의 옛
기록은 갱신하지 않는다. config·클래스·레벨이 다른 비교는 수치를 볼 수 있지만 이
재검토 증빙으로 쓰지 않는다. 패키지의 이득을 개별 부품의 독립 효과로 인용하지 않는다.

거부당하면 **사유를 고치고 다시** — 되감기가 아니라 그게 루프다. 자주 나오는 것:
- `베이스 미확인: '…'` → 그 베이스는 실재하지 않는다. KB에서 실제 이름을 찾을 것
- `티어 범위 밖` → 그 부위에 안 붙는 접사다(`spawn_weights` 확인)
- `어센던시 노드 …가 시작 노드에서 닿지 않는다` → 경로를 이어야 한다(#26)
- `어센던시 **시작 노드** …는 PoB가 자동 배정한다` → `tree_nodes`에서 뺄 것
- `룬 소켓 N칸 > 6칸 — PoB가 표현하지 못한다` → `Sockets:` 줄을 6칸으로 줄이고
  **넘치는 칸의 값은 따로 주입한다**(#120). 인게임 가부가 아니라 **PoB 한계**다:
  룬 드롭다운이 6개뿐이라 그 아이템을 클릭하는 순간 예외로 죽는다(계산 경로에서는
  안 터져 여기서만 잡힌다). 주입 경로는 둘 —
  `ItemSpec.substitutes`(그 아이템에 붙고 **산출물에 추산으로 자동 기록**) 또는
  config `customMods`(전역). 실측 2026-08-25: 7칸을 6칸+`customMods` 4줄로 옮기니
  `Life`·`Spirit`·`TotalEHP`·`CombinedDPS`가 **소수점까지 같았다**.
  ⚠ 두 가지를 함께 보정할 것 — ①주입 줄에는 `increased effect of Socketed Runes`
  증폭이 **안 곱해진다** ②`per Socket filled` 모드는 **실제 룬 수**를 세므로
  (`RunesSocketedIn`) 줄어든 칸만큼 그 값을 직접 더해 줘야 한다

### 3. `validation.json`을 읽는다 — 이것이 정본이다

`artifacts/builds/<id>/validation.json`에 실측 스탯·적법성·트리 판정이 남는다.
**보고에 인용하는 수치는 여기서 가져온다.** 세션 기억이나 탐색 단계 출력이 아니다.
최종 추천은 `purpose`와 `optimization_readiness`도 함께 확인한다. `ok:true`인
탐색 조립은 추천 완료가 아니다. `ready_with_exceptions`이면 수용한 정확한 한계와
미수행 항목을 보고서에 남긴다. `ready`도 선언한 탐색 범위의 충족이며 전역 최적이나
인게임 검증을 뜻하지 않는다.
`item_sockets`에는 PoB가 아이템별로 읽은 칸 수·예산(베이스/유니크 + **트리 부여**)이
그대로 남고, 막지 않은 `warnings`도 함께 남는다(#120) — `strict=False`로 진단만 했을
때도 남으므로 "알고도 넘겼다"가 기록에 보인다.

### 4. 고칠 것을 반영하고 **2로 돌아간다**

스펙을 고쳐 재조립한다. 매 회차가 파일로 남으므로 무엇이 언제 바뀌었는지 추적된다.
자원·실사용 핵심 목표를 만족하지 못하면 `build-generation`의 전체 구성 비교로 돌아간다.
주력기·보조·장비·트리 교체를 막거나 기존 컨셉 보존을 조립의 전제로 삼지 않는다.

### 5. 재개 — 새 저장 위치를 만들지 않는다

세션이 끊기거나 컨텍스트가 차면 **직전 산출물의 `spec.json`을 먼저 읽는다**.
`assemble_pob`가 실제 조립에 사용한 스펙(자동 채움 후)을 저장하므로, config·젬 설정·
능력치 선택·출처 도장을 그대로 다음 입력으로 쓴다. 편집본도 같은 폴더의 `spec.json`에
저장하고 재조립한다. 설계 판단·검증 큐는 `parse_design_doc`로 함께 이어받는다.

`spec.json`이 없는 옛 산출물만 `build.pob`의 전체 코드를 읽어 복원한다:

```
restore_pob_spec(build_code=<build.pob의 전체 문자열>)
```

반환의 `build_spec`을 쓰기 전에 **`notes`·`needs_decision`·`damage_comparable`을 읽고**
복원되지 않은 설정을 확인한다. `parse_pob`은 내용 요약이므로 재계산 입력을 대신하지
못한다. 복원본에서 바꾼 수치는 새 조립으로 검증한다.

⛔ 스펙 편집본을 둘 새 디렉터리를 만들지 말 것. **사용자 판정 2026-08-09(제안 E):
스펙 파일도 `artifacts/builds/<id>/`에서 관리한다** — 빌드별 폴더가 이미 있으니
거기가 자리다. 저장 위치 신설은 없다(철칙 1 해소).

그래서 한 빌드의 모든 것이 한 폴더에 모인다:

```
artifacts/builds/<id>/
  build.pob          조립 산출물 (PoB 공유 코드)
  validation.json    실측 스탯·적법성·트리 판정
  spec.json          실제 조립에 사용한 스펙 — 재개·다음 회차 편집의 입력
```

`artifacts/`는 gitignore 파생물이라 git에 남지 않는다. **정본으로 남길 것은 커밋
가능한 자리에 따로 둔다** — 폴더가 지워져도 잃으면 안 되는 결정은 `docs/`에.

## 금지 사항

- ⛔ **장비를 대화에 들고 반복하기** — #27이 그렇게 났다. 조립하고 파일을 볼 것
- ⛔ 탐색 단계(`compute_pob`) 수치를 **최종 보고에 인용** — `items_legal`이 통과해도
  그건 "장비가 실재한다"이지 "이 값이 정본"이 아니다
- ⛔ `assemble_pob` 없이 "빌드 완성" 보고 — 적법성 전수 검사를 안 거친 것이다
- ⛔ 거부 사유를 **우회**(strict=False로 넘기기) 후 진행 — 진단 목적에만 쓴다
- ⛔ 룬·희귀를 손으로 조립 — `optimize_runes`·`optimize_rare`의 `text`를 그대로 쓴다

## 이 스킬만으로는 부족하다 (철칙 5)

스킬은 문서고, 문서 규율은 **인용까지 하고도 어겨진 전례**가 있다. 그래서 1순위는
도구였다 — `compute_pob`이 이제 `items_legal`·`req_shortfall`을 **매 반환에** 싣는다
(#27·#29). 이 절차는 그 위에 얹는 순서이지 유일한 방어선이 아니다.
