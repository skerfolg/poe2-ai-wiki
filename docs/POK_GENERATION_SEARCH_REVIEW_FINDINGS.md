**수정한 개선 가설:** 검증 큐를 완료 보고용으로만 사용하지 말고, 사용자 목적을
지탱하는 가정이 약해졌을 때 현재 구현의 채택을 재검토하는 질문으로 사용한다.
예컨대 ‘회복 보장을 쓰지 않는다’에서 그치지 않고 ‘이 회복 없이 같은 운용 목표를
만족하는가, 아니면 다른 공급/주력 구조가 나은가’를 비교한다. 이것은 무조건 보수적인
빌드를 선택하거나 미검증 기재를 금지하는 규칙이 아니다. 고점과 실패 비용을 사용자의
목적에 맞게 비교하자는 제안이며 효과는 신규 평가 전에는 미입증이다.

v2 생성 지침은 필요조건/현재 공급자 분리, 초기 선택 재개방, 완성 묶음 비교,
최적화 범위의 한계를 이미 요구한다. 따라서 같은 문구를 더 강하게 반복하는 안은
독립적인 개선 가설이 아니다. 다만 현재 지침을 읽었다는 사실로 과거 시험에 그 지침이
전달됐다고 소급할 수 없으므로 실행별 프롬프트·소스 버전 대조가 필요하다.

유력한 추가 가설은 **불확실성을 기록하는 행위가 선택을 재검토하는 행위를 대신했다**는
것이다. H2의 제출문은 수치와 미검증을 정직하게 설명하지만, 사용자에게 필요한 것은
그 사실을 감안한 실용적인 선택이다. 이는 아직 판단 가설이며 원본의 대안 생성·기각
기록과 과제 요구를 읽기 전에는 원인으로 확정하지 않는다.

## 반증 가능한 개선 후보

1. 발견: 자동 후보 범위 밖의 구체화 가능한 재료를 주었을 때 완성 조합을 만드는가.
   재료를 줘도 같은 약한 선택이면 검색 확대만으로 해결된다는 가설을 기각한다.
2. 조합: 새 슬롯·자원·경로를 여는 부품을 평가할 때 필요한 동반 변경을 스스로
   구성하는가. 완성 답안과 점수를 주고 고르게 하는 시험으로 대체하지 않는다.
3. 선택: 핵심 공급의 불확실성에 대해 유리/불리한 조건에서 후보 우열이 뒤집히는
   경계를 찾는가. 정밀 측정이 불가능하면 근거 있는 범위와 실패 시 운용을 비교한다.
   임의 가동률이나 손계산을 사실로 만들지 않는다. 불확실성 표시만 늘면 개선 실패다.
4. 비용: 기존 원문과 필요한 결과를 같은 수준으로 제공해도 PoK 경로에서 복구·기록
   작업 때문에 중요한 대안 비교가 누락되는가. 단순 호출 수를 품질 점수로 쓰지 않는다.

새 시험은 아직 실행하지 않는다. 개발에 사용한 아이스샷과 H1/H2는 회귀 자료로
남긴다. 신규 평가 자료는 결과 열람 전에 분리해야 하며 패치·투자·목적·측정 조건이
다른 참조의 표기 DPS로 우열을 매기지 않는다.
