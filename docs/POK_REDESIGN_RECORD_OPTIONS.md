# R2 설계 기록 소유·저장 후보 검토

2026-11-01 결론: 기존 작업 공간이 현재 참조를 소유하고 서버는 불변 체크포인트를 보존하는
B를 [상세 계약](POK_REDESIGN_CONTRACTS.md)으로 채택했다. 아래는 채택 전의 관측/대안 비교다.
새 서비스·DB·모듈 경계/데이터 폴더 이동은 도입하지 않았다. 계약 채택은 저장/소비자 구현 완료가 아니다.

2026-10-31, R1 추가 실험 대기 중 작성한 계약 준비안이다.
첫 과제의 관측과 [형식 감사](POK_DESIGN_FORMAT_AUDIT.md)를 입력으로 삼지만,
추가 과제/앵커 비교의 결과를 대신하지 않는다. 구현·저장 경계 변경·제품 기본값은 확정하지 않았다.
진행과 다음 행동은 [Current Plan](CURRENT-PLAN.md)을 따른다.

## 현재 구현에서 확인한 경계

- `artifacts/store.py::record_build`는 파일 묶음을 기록한다. `_record`는 기존 경로를
  허용하고 파일을 직접 쓰므로, 이 API의 호출만으로 불변 리비전·배타적 생성·원자적 게시가 보장되지는 않는다.
- `new_build_id`는 날짜+slug와 경로 존재 여부로 충돌을 피한다. 논리 설계 ID나 동시 갱신 CAS 계약은 아니다.
- `record_build`의 content_hash는 파일 이름과 전달받은 문자열을 순서대로 해시한다.
  새 계약에서 이를 실제 저장 바이트·원본 XML·측정 입력의 전체 동일성 해시와 같은 것으로 취급하지 않는다.
- `engine/assemble.py`가 저장할 파일 묶음을 조합하고 `artifacts`는 기록만 한다.
  `artifacts`가 PoB/engine을 역으로 해석하도록 바꾸지 않는다.
- `mcp/tools/constraints.py::parse_design_doc`가 기존 빌드의 Markdown을 읽는다.
  현재 추출 파서는 새 역할/의존/리비전을 이미 소유하는 기록 저장소가 아니다.
- UI BuildDocument는 XML/원본 XML/revision을, undo는 XML과 label을 보존한다.
  새 설계가 포함된 제안을 적용하면서 기존 XML undo만 수행하면 두 기록이 어긋날 수 있다.

이 관측은 읽기 전용 코드 확인이다. 동시성/게시의 실패를 실제 재현한 새 결함 보고나
현행 API 전면 폐기 결정으로 확대하지 않는다.

## 구현 전 확인한 기존 계약의 차이

`artifacts/design.py`의 모듈 주석은 기존 Markdown 최소 계약을 넘는 스키마화를
금지한다. 반면 개정 BLUEPRINT는 구조화된 설계 정본에서 문서를 생성하는 방향을
채택했다. 이 차이를 기존 파서가 이미 새 정본을 구현했다는 근거로 읽지 않는다.
R2에서는 옛 파서의 호환 책임과 새 기록의 책임을 명시하고, R3에서 새 경로가 준비된 뒤
주석·BUILD_DESIGN·스킬의 옛 규칙을 함께 정렬해야 한다. 원문/미지 정보 보존 없이
옛 문서를 새 필드로 강제 변환하는 방식은 이행 계약을 충족하지 않는다.

실제 import-linter 설정은 `mcp → engine → (index|pob|live|cost|learning|artifacts)
→ kb → (i18n|common)`이며 `|`로 구분된 같은 층은 서로 독립이다. 따라서 향후
artifacts 안에 순수 기록 형식/렌더를 추가할 수 있는지 검토할 때도, 그 모듈에서
engine/PoB 계산기를 가져와 근거를 재판정하는 의존은 허용된 것으로 전제하지 않는다.
계산 결과와 실제 입력을 해석하는 책임은 상위 계층에 두는 후보를 검토한다.
이는 `pyproject.toml`의 현행 계약을 읽은 준비 기록이며, 파일 위치·새 공개 API를
확정하거나 경계를 변경한 결정은 아니다.

## 두 후보

| 항목 | A: 서버가 논리 설계의 현재 상태를 소유 | B: 호출자 작업 공간과 불변 체크포인트 |
| --- | --- | --- |
| 편집 정본 | PoK가 design_id별 현재 리비전/헤드를 저장 | 호출자의 현재 설계 객체. PoK는 명시적으로 전달받은 기록을 검사·변경·렌더 |
| 보존 | 변경마다 리비전 저장 후 현재 헤드 갱신 | 체크포인트는 별도 산출물로 보존하고 부모 리비전/구성 참조를 명시 |
| UI | 서버 헤드와 UI XML revision의 조정을 구현 | UI의 한 적용 동작에서 XML과 설계 객체/참조를 함께 갱신 |
| CLI/다른 PC | 서버/산출물의 같은 헤드를 재개 | 사용자가 선택한 체크포인트를 재개. 다른 PC로 해당 산출물 전달 필요 |
| 동시 편집 | 서버가 expected_revision으로 전역 충돌을 감지 | 작업 공간 안의 충돌은 호출자가 확인. 독립 체크포인트의 분기는 보존하고 자동 병합하지 않음 |
| 부담 | 잠금·헤드 복구·중복 저장·서버 상태 수명·동기화 계약이 추가됨 | 호출자의 현재 참조 보존과 체크포인트 선택 계약이 필요함 |
| 주요 위험 | UI와 서버가 같은 결정을 서로 다른 현재 상태로 편집할 가능성 | 단순히 가장 최근 파일을 골라 다른 분기를 조용히 현재 상태로 오인할 가능성 |

잠정 선호는 B다. 이유는 기존 UI 작업 공간과 독립 산출물을 유지하면서 또 하나의 가변
서버 저장소를 만들지 않을 수 있기 때문이다. 단, 실제 CLI 재개와 멀티 PC 사용에서
현재 참조를 신뢰성 있게 보존하지 못하면 이 선호를 재검토해야 한다.
추가 앵커 비교와 R2 계약 검토 전에 B를 채택했다고 보고하지 않는다.

두 후보 모두 새 최상위 폴더/서비스/데이터베이스를 필요 조건으로 삼지 않는다.
정확한 저장 위치·모듈 경계·현재 참조 소유는 기존 경계에서 구현 가능한지 확인하고,
변경이 필요한 경우 [구조 규칙](PROJECT_STRUCTURE.md#0-거버넌스--구조-변경-규칙-최우선)에 따라
사용자와 구체적으로 협의한 뒤 적용한다. 이 문서는 그 합의를 대신하지 않는다.

## 어느 후보든 필요한 의미

다음은 필드 이름을 확정한 스키마가 아니라, 빠뜨리면 안 되는 독립 정보다.

| 정보 | 구분해야 할 내용 |
| --- | --- |
| 논리 설계 | 안정적인 설계 ID, 부모 리비전/분기, 기록 형식 버전 |
| 결정 | 안정적인 항목 ID, 사용자 고정/메커니즘 필수 조건/잠정 구현/성능 후보라는 역할 |
| 상태 | 채택·기각·보류와 근거의 확인 수준을 별도로 표현 |
| 조건/공급자 | 무엇이 필요한가와 지금 무엇으로 충족하는가. 공급자는 교체 가능하고 하나의 공급자가 여러 조건을 충족할 수 있음 |
| 관계/비용 | 의존·대체·무효화/재검토, 슬롯·포인트·자원·조작 비용과 알려지지 않은 값 |
| 열린 질문 | 주장, 판정 방법/관측 조건, 누구의 판단/인게임 관측이 필요한가 |
| 실물 구성 | 계산 스펙 또는 원본 XML 참조와 해시, 선택한 세트/모드, 해당 도구/PoB 버전 |
| 근거 | 실제 입력에 결박한 계산·KB/인사이트·인게임 관측, 범위·미측정·출처와 리비전 |
| 표현 | 같은 기록에서 만든 design.md/UI, 기존 원문과 미지 정보의 보존 참조 |

설계 메타데이터를 기존 BuildSpec에 임의로 집어넣는 방법은 피한다. 현재 엄격한 입력 계약은
계산에 해당하지 않는 알 수 없는 키를 거부한다. 필요한 연결은 별도의 명시적 계약으로 제안한다.
복원 표식이나 도구 호출 도장을 계산/성립성/추천 품질의 인증으로 삼지 않는다.

## 앵커 시험의 초기 읽기에서 남은 의미 문제

추가 시험4개가 종료된 뒤의 비채점 읽기 기록은
`artifacts/reviews/redesign-r1-followup-evaluation/qualitative-notes-anchor-v1.json`에 있다.
기록형2개는33/35개의 ID와 네 역할을 사용했고 중복 ID·미해결 참조는 없었다.
이 사실만으로 변경 영향의 누락이나 오래된 근거가 없다고 판단하지 않는다.
자유 서술2개에도 조건/공급자·변경 손익·실제 구성/측정 연결이 있으므로 의미가 같은
근거는 동등하게 인정해야 한다. 아직 양식의 효과나 부담 우위를 판정하지 않았다.

검토 예는 ‘처치 없는 공격 지속성’과 ‘재생만으로 주력 비용을 충당’의 범위 차이다.
후자는 선택한 보수적 자원 전략으로 타당할 수 있지만, 다른 공급 경로로 바꿀 수 없는
보편적인 게임 성립 조건이라고 표현하면 공급자 교체를 불필요하게 막는다.
R2 계약은 필수 조건이 어느 채택안/전략에서 필수인지와 현재 공급자·대체 가능성을
함께 표현할 수 있어야 한다. 이 관측만으로 해당 시안의 전략을 잘못됐다고 판정하지 않는다.

중복 ID·참조 해소·구성 해시·명시된 의존 변경은 도구가 검사할 수 있다. 반면 어떤
문구가 실제 메커니즘의 필요조건인지에 대한 판단은 필드를 채웠다는 사실로 증명되지
않는다. 형식 검사 결과와 근거에 의한 의미 검토를 분리하고, 이 둘을 하나의 완료 도장으로
합치지 않는 후보 계약을 검토한다. 새 필드 이름이나 저장 경계를 확정한 것은 아니다.

## R2에서 후보를 결정하기 전에 확인할 예제

1. PoB가 아직 없는 초기 조건 기록을 저장하고 같은 기록에서 재개한다.
2. 동일 메커니즘의 공급자를 바꿔도 필수 조건은 유지되고, 영향받은 비용·근거만 재검토 대상으로 나온다.
3. 메커니즘 자체를 바꾸면 종속 조건/선택의 영향을 신고하고 AI가 유지/폐기를 판단한다.
4. 실제 구성만 바뀌거나 설계 설명만 바뀌었을 때 측정 근거의 재사용 범위를 구분한다.
5. UI에서 설계+XML 제안을 검토·적용·undo하고 늦게 도착한 결과를 현재 버전으로 표시하지 않는다.
6. 같은 부모에서 나온 두 독립 변경을 보존한다. 최신 시각 파일을 조용히 승자로 만들지 않는다.
7. 원래 Markdown/미지 XML/비활성 세트와 기존 artifact ID를 보존한 채 가져오기·내보내기·복귀한다.
8. 한쪽 파일만 기록되거나 저장이 중단됐을 때 완성된 리비전으로 읽지 않고 원본으로 복구한다.

현재는 이 예제들의 계약 후보를 준비한 단계다. 실제 성공·실패 fixture, 저장 원자성,
버전 호환, 사용자 고정 변경의 처리와 추천 판정은 R2에서 확정하고 R3~R6에서 구현·검증한다.
