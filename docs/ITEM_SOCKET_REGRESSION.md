## 실제 재현한 영향

원본의 최초 읽기는 3소켓/3룬이었다. 같은 룬을 다시 선택하는 PoB 편집기 콜백
`UpdateRunes → BuildAndParseRaw` 한 번으로 6소켓/6룬이 됐다. 공속 문구는8→16%,
상태이상 강도는20→40%, 장갑 자체 ES는133→144, 회피는413→449로 증가했다.
다음 저장·재입력은9소켓이 되어 `UpdateRuneControls`에서 실패했다.
**표시만 중복된다는 가설은 반증됐다.** 이것은 철회된 원본의 결함 재현이며 유효 성능이 아니다.

수정한 3칸 재현본·2칸 장갑·룬 효과 증폭 완드는 각각 편집 콜백→저장→재입력을
3회 반복해 소켓·룬·컨트롤 수와 계산값을 보존했다. 일반/마법 두 줄 헤더도 검사했다.
3칸 재현본의 왕복 성공은 그 장비의 획득 가능성을 승인한 것이 아니다.

원본 전체 스펙의 15개 장비·플라스크·참도 다시 검사했다. 투구3홈·갑옷4홈·신발3홈·
장갑3홈은 선언된 획득 경로로 설명되지 않아 엄격 조립을 거부했다. 소유 활의3홈은
추가 획득 경로가 스펙에 없어서 `acquisition_unproven`으로 남겼다. 이것은 사용자의
실물 활이 존재하지 않는다는 판정이 아니며, 실물 능력치를 바꾸지 않았다.
재현 전후 원본60파일의 해시가 같고 대체 빌드는 생성하지 않았다.

사용자 설치 PoB 0.23.1의 `Item.lua`와 `ItemsTab.lua`는 핀 계산기와 줄바꿈 정규화 후
내용이 같았다. 검증은 이 실제 소스의 편집기 함수를 실행했으며 별도 모의 파서가 아니다.

## B/C 더블클릭 재현과 완료 판정 정정

아이템 더블클릭은 곧바로 `SetDisplayItem`을 부르는 동작이 아니었다. 실제
`ItemListControl:OnSelClick`은 `new('Item', item:BuildRaw())`로 복사한 뒤 편집창을 연다.
앞선 검증은 이 앞단을 빠뜨렸다. 따라서 **빌드 파일 열기·계산 성공을 아이템 상세보기
성공으로 확장했던 완료 판정은 잘못됐다.** 이 경로의 `ItemListControl.lua`도 사용자
설치판과 핀 소스가 줄바꿈 정규화 후 동일함을 확인했다.

| 원본 사례 | 최초 상태 | 실제 더블클릭 결과 |
| --- | --- | --- |
| B Gelid Staff | 4소켓·4룬 | `BuildRaw` 재파싱 후8소켓·8룬, `UpdateRuneControls`의 nil 오류 |
| C Vaal Gloves | 6소켓·6룬 | 재파싱 후9소켓·9룬, 같은 오류 |

B는 모드 뒤에 남은 소켓/룬 선언 한 벌이 복제되고, C는 내보낸 코드에 이미 같은
선언 두 벌이 들어 있었다. 둘 다 #193의 잘못된 선언 위치에서 이어진다. 원본 전수
검사는 장시간 파싱·tooltip 비교 계산 때문에 완료하지 못했으며 성공으로 세지 않았다.

B5개·C6개 아이템은 진단 사본에서 선언 구조만 교정했다. B는 한 벌을 헤더로 옮겼고,
C는 정확히 같은 두 선언 중 한 벌을 보존해 헤더로 옮겼다. **소켓/룬 선언 외 모든
줄은 값과 순서까지 원본 그대로다.** C의 보존한6개 슬롯 선언은 내보내기 전 최종 명세
3종과 모두 같았다. 룬 선택이나 품질·접사를 임의로 바꾸지 않았다.

A 원본19개, B 사본19개, C 사본18개를 실제 더블클릭 콜백으로 검사해 **56개 모두
성공**했고, 최초 파싱과 재파싱의 소켓·룬 개수가 같았다. 원본 공유코드 SHA-256과
처음 추출한56개 본문도 그대로 보존됐다. 진단 사본은 원본과 별도로 보관한다.
이 사본은 편집 오류 조사용이며 획득 가능성·고유 아이템 선택·패시브 최적화나
성능 개선을 인증한 새 빌드가 아니다. 생성 품질 #188은 계속 미해결이다.

새 편집 어댑터는 별도 PoB 프로세스에서 실제 콜백을 실행한다. `checked`는 요청한
아이템 모두에서 검사 결과가 나왔는지를, `compatible`은 전부 성공했는지를 뜻한다.
누락·시간초과·실행 실패는 미검증으로 반환한다. 엄격 조립은 두 조건이 충족되지 않으면
공유코드 생성 전에 거부하고 검사 결과를 검증 기록에 남기도록 연결했다. 조립 연결
시험은 진행 중이며, 실제 Windows 화면 조작 검증도 아직 미확인이다.

## 획득 판정의 근거와 한계

- 일반 홈 규칙은 종류별 보드 규칙으로 관리하고 근거 등급을 `SUPPORTED_INFERENCE`로
  남겼다. PoB `socketLimit`는 일반 제작 예산으로 쓰지 않는다.
- exceptional 추가 홈은 `items[].socket_sources=["exceptional"]`로 명시한다.
  이 필드는 목표 장비의 획득 경로 선언이며, 실제 매물 보유나 획득 확률의 증명은 아니다.
- exceptional 추가 홈과 초과 품질은 같은 결과로 중복 선언할 수 없다. 단순히 품질이
  높다는 이유만으로 출처를 추측하지 않는다.
- `Corrupted`는 별도 타락 옵션과 추가 홈을 동시에 주는 증거가 아니다.
  `Twice Corrupted`도 두 번째 추가 홈을 무제한으로 만드는 규칙으로 해석하지 않는다.
- 전직의 추가 Rune 전용 홈에는 다른 종류의 장착물을 넣을 수 없다.
  이름에 Rune/Idol이 있는지 추측하지 않고 같은 스냅샷의 원본 종류를 사용한다.
- PoB XML에는 exceptional 획득 경로 필드가 없다. 원래 `spec.json`과 검증 결과를
  보존해야 한다. 공유코드만 재입력해 출처가 사라진 경우를 자동으로 합법 인증하지 않는다.
- 이 검사는 알려진 획득 규칙의 모순을 차단한다. 게임 전체의 모든 제작 경로,
  가격·공급·인게임 작동을 인증하는 검사는 아니다.

## 시험 결과

이전 #192~194 수정 시점의 중복 제외 결과는 **단위1,840개 + PoB 통합26개 = 1,866개
통과, 9개 skip**이다. 아래의 이번 #195 추가 시험을 합친 최종 전량 수가 아니다.
전체 단위와 관련 통합4파일을 함께 실행해 1,865통과/9skip/1실패를 확인했다.
실패는 새 통합 파일의 환경 선언 형식 누락이었다. 기존 fixture 내부의 환경 검사를
파일 수준 `skipif`에도 명시한 뒤, 해당 검사·문서 검사·native 왕복21개를 재실행해
모두 통과했다. 기존 통과 시험을 중복해 더하지 않았다.

로컬에 빠져 있던 Accuracy·Incision 원시 fixture2개는 이전에 복원한 같은 스냅샷
파일로 경로만 연결했다. 시험의 조건·검증식은 바꾸거나 건너뛰지 않았다.
통합 전체를 이번에 전량 실행한 것은 아니며, 변경과 관련된 조립·홈 획득·편집 왕복·
기존 아이템 왕복4파일을 실행했다. Ruff·mypy(153파일)·의존 방향 검사도 통과했다.
작업 상태 문서 검사도 오류0/경고0으로 통과했고, 최종 문서 수정 후 백로그 검사14개를
다시 통과했다. 이는 빌드의 인게임 성능 검증 횟수에 포함하지 않는다.

이번 #195에서는 편집 어댑터 **단위9개·native 통합7개**가 추가로 통과했다. 실제 원본
더블클릭 오류와 사본56아이템 대조는 별도 재현 증거다. 이후 조립 출고 연결과 전체 단위·관련 통합 검증을 마쳤으며 최종 수는 아래 후속 검증 절에 기록한다.

별도 새 stdio MCP에서는 원본 장갑의 룬 최적화가 홈 예산으로 거부됐고, 계산은
수치를 반환하면서 `items_legal=false`, `item_sockets_legal=false`를 냈다.
엄격 탐색 조립은 `ok=false`로 공유코드를 만들지 않았다. 이전 상주 서버를 갱신했다고
주장하지 않는다. Windows 화면 조작 미검증과 생성 품질 미해결도 그대로 남긴다.
