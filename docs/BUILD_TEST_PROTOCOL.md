# 실전 빌드 테스트 프로토콜 (무개입)

> **대상**: 빌드 생성을 수행하는 세션
> **작성 계기**: P5 이후 실전 검증 (사용자 결정 2026-08-04)
> 관련: [ROADMAP](ROADMAP.md) P5 · [BUILD_DESIGN](BUILD_DESIGN.md) 설계 규격

---

## 1. 무엇을 재는가

**"이 빌드가 좋은가"가 아니라 "도구와 규율이 스스로 작동하는가"** 를 잰다.

측정 대상은 파이프라인 단독 성능이다. 도구를 만든 세션이 생성에 끼어들면
"사람+도구"의 성능을 재게 되고 — 그건 자기 채점이다 — 정작 알고 싶은 값을
영영 모르게 된다.

실측 배경: 지금까지 **인게임까지 완주한 빌드는 1건**(`20260730-liminal-curse-bolts`,
P3)뿐이다. 이후 3건은 전부 DPS·EHP 계산 전에 멈췄다. 차단을 잡아내는 능력은
검증됐지만 **완주 경로는 P4·P4.5·P5의 장치가 붙은 뒤로 한 번도 재현된 적이 없다.**

---

## 2. 무개입 규칙

1. **구조 세션에 묻지 않는다.** KB·MCP 도구·인사이트만 참조한다. 도구가 부족해
   막히면 그 자체가 결과다 — 구해주면 그 발견이 사라진다.
2. **막히면 막힌 채로 기록하고 멈춘다.** 좌초는 실패가 아니라 **가장 값진 데이터**다.
   실제로 v6·v7·시신걸음이 그렇게 남아 있어서 진단이 가능했다.
3. **완성도를 위해 되돌아가 고치지 않는다.** 세 번 고쳐 완성한 빌드와 한 번에 나온
   빌드는 결과물이 같아도 파이프라인 평가는 정반대다. 고쳐야겠다는 판단이 들면
   **고치지 말고 그 판단을 기록**하라 — 그게 "도구가 못 한 것"의 목록이 된다.

> 사람이 게임 지식으로 판정하는 것은 개입이 아니다(원래 사용자 게이트의 몫).
> 개입은 **구조 세션이 설계·도구 사용을 대신 해주는 것**을 말한다.

---

## 3. 반드시 남길 것

### ① `artifacts/builds/<id>/design.md`

[BUILD_DESIGN](BUILD_DESIGN.md) §4 규격대로. 특히 **도달 지점과 좌초 사유**를
헤더 `- 상태:` 줄에 명시한다. 기존 3건이 좋은 본보기다.

### ② 도구 성적표

**`pok` MCP 도구는 자동으로 남는다** — 손으로 옮겨 적지 않아도 된다:

```bash
PYTHONPATH=src python -m pok.common.telemetry
```

`var/tool-calls.ndjson`에 예외(`error`)·명시적 실패(`failed`)·**조회 0건**(`empty`)이
쌓인다. 특히 `empty`가 값지다 — 0건은 실패가 아니라 KB 갭이거나 표기 오류라는
신호이고, 둘은 대응이 정반대다(B-1 실측).

**자동으로 안 남는 것**: 스킬 등록 실패·Bash 오류·경로 오해는 MCP 밖이라 못 잡는다.
그건 아래 표에 손으로 적는다. 각 좌초·오류에 대해 **어느 도구가 잡았는지 / 놓쳤는지**:

| 잡은 것 | 놓친 것 |
|---|---|
| 예: `check_constraints`가 정신력 축 점유 초과 검출 | 예: 인사이트 조회를 안 해 차단을 장비 계산 후에야 발견 |

"놓친 것"이 다음 작업 목록이 된다.

### ③ 사람이 개입한 지점

있었다면 **어디서·왜**. 없었다면 "무개입 완주"라고 명시.
이 항목이 파이프라인 성숙도의 직접 지표다.

## 4. 빌드 선정 — 축이 달라야 한다

같은 계열을 반복하면(v6→v7처럼) 같은 지식만 재확인된다. **서로 다른 축 3개**를
목표로 한다:

| 축 | 예시 |
|---|---|
| 딜 방식 | 직접 시전 / 트리거 / 미니언 |
| 방어 축 | 생명력·아머 / 에너지 보호막 / 룬 수호 |
| 무기 계열 | 근접 / 원거리 / 주문 |

이미 다룬 영역(트리거 연쇄·정신력 스태킹·로우라이프 점유)은 인사이트가 두꺼우므로,
**얇은 영역을 고르면** 검증 가치가 크다.

**덤**: 능동 탐사 가설 12건이 판정 대기 중이다(`find_hypotheses`). 아직 아무도 안
써본 조합이라 그중 하나를 컨셉으로 삼으면 검증과 학습이 한 번에 된다.

## 5. 도구 사용 규율 (요약)

상세는 [BUILD_DESIGN](BUILD_DESIGN.md)·`skills/build-generation/`. 특히:

- **KB 질의는 `pok` MCP 도구로.** `knowledge/` NDJSON을 Grep/Read로 뒤지지 말 것
  (실측: 파일 탐색 7분 vs 도구 1초).
- **설계 전에 `search_insights`로 차단 경로부터 조회.** 특히 "무엇이 **안 되는가**"의
  기록은 실패한 설계에서만 얻어져 레코드 필드에는 없다. `scope="durable"`이면
  시즌을 넘어 유지되는 것만 나온다.
- **연쇄에 의존하면 각 화살표를 개별 검증한 뒤** 장비·수지 계산에 들어간다.
  성립 조건이 미해결인데 하위 목표를 최적화하지 말 것.
- **추측 금지, PoB 델타로 측정**(AD-8). 미측정은 "미측정"으로 남긴다.

## 6. 브랜치·충돌 회피

- 생성 세션: **`artifacts/builds/` 산출물만** 만진다.
- 구조 세션: `src/`·`docs/`만. 결과 통보 전까지 **도구를 바꾸지 않고 대기**한다.

이유: 테스트 중 도구가 바뀌면 지면이 움직여 빌드 간 비교가 무의미해진다.
급한 결함으로 도구를 고쳐야 하면 **"N번째 빌드부터 도구가 바뀌었다"고 기록**한다.

## 7. 완료 후

결과를 구조 세션에 통보한다. §3의 세 항목이면 충분하다.

구조 세션이 할 일: 채점 → 놓친 것을 도구·규율로 흡수 → 다음 빌드에서 **같은
결함이 재발하지 않는지** 확인. 그 재발 방지가 확인되면 학습 루프가 실제로
작동한다는 증거이고, P6 진입 판단의 근거가 된다.
