## 전달 감사

최종 응답이 있는 5개 모두 `pob_code` 필드는 디코딩에 실패했다. 각 최종 응답의
`build_id`가 명시한 저장 `build.pob`는 모두 정상 디코딩됐고 대응 `build.xml`과 일치했다.
저장 파일을 명시적으로 제공했으므로 이를 최종물로 검사하되 코드 필드의 전달 오류를
별도로 남긴다. 최신·최강 중간안을 대신 선택하지 않았다.

개선 H1 최종2의 설계 문서는 “코드 문자열은 저장 build.pob의 내용과 일치한다”고 적었지만,
실제 최종 응답 코드 필드는 디코딩에 실패했다. 최종 응답은 저장 파일을 정본으로 쓰라고
안내했다. 문서 주장·코드 필드·저장 파일의 불일치는 그대로 보존하며, 계산 성공으로 상쇄하지 않는다.

근거: `artifacts/reviews/r5-submission-delivery-audit-v2.json`의 원본 해시·파일 관계·오류.
수집 목록은 `r5-outcome-inventory-collected-v1.json`이며, 8회 시도와 유효 최종 응답5개를
구분한다. 목록 검사 오류0은 빌드 오류0을 뜻하지 않는다.

기록된 최종 agent_message JSON과 answer.json을 대조했으며5개 모두 전체 객체와 코드
필드가 같았다(r5-answer-event-consistency-v1.json). 따라서 최종 이벤트 기록 이후
수집기가 answer.json에 저장하면서 바뀌었다는 가설은 이 대조에서 지지되지 않는다.
모델 내부나 그 이전 호스트 경로의 원인을 특정한 결과는 아니다.

공백을 모두 제거해도5개 모두 불일치했다(r5-code-transcription-diff-v1.json).
중간 문자 차이와 짧아진 결과가 함께 있어 단일 잘림 원인으로 설명하지 않는다.

동결 캠페인의 product_campaign은 redesign_run.ANSWER_SCHEMA를 사용하며 이 스키마는

계약 자체에도 긴 문자열 재전사 부담이 있었다. 이것이 개별 손상의 단독 원인이라는
인과 증명은 아니다. 두 제품에 공통된 계약이므로 장비/패시브 선택 품질의 제품 간
차이를 이 사실만으로 설명할 수도 없다. 동결 실행기는 변경하지 않았으며 새 전달
계약의 실제 모델 검증은 별도 프로필로 진행해야 한다.

## 독립 검증

평가용 데이터·캐시는 참가자 공간과 분리했다. 최종 저장 코드를 복원할 때 첫 스탯 세트를
임의 선택하지 않았고 계산은 `input_policy=explicit`로 요청했다. 원래 설정을 변경하지 않는다.
BuildSpec 복원에 의한 계산이므로 원본 XML 직접 계산과의 동등성은 별도 확인 대상이다.

첫 기준 H1 최종물은 faithful 복원·선택 미결0, 장비/주얼17개 legal, 연결된 트리,
가지치기0, 일반123/전직8, 원소·카오스 저항 각각75를 확인했다. 계산 계약은 자동 입력
보완 없음, 추천 검사 미수행, 게임 성립 미인증이다.

| 독립 검증 표본 | 복원/선택 미결 | 장비·주얼 검사 수 | 일반/전직 | 트리·장비·소켓 | 네 저항 |
|---|---|---:|---|---|---|
| 기준 H1 최종1 | faithful / 0 | 17 | 123/8 | 검사 통과, 가지치기0 | 각75 |

5개 모두 복원·계산·조건 진단을 마쳤다. 장비/주얼 개별 검사는 합계90건이며 모두 legal이다.
이 표는 알려진 검사 범위의 결과이며 메커니즘 성립이나
고투자 품질, 원본 XML 직접 계산과의 동등성, 실전 유지율 판정이 아니다.

원본 XML 직접 계산은 별도 캐시 공간에서 `use_cache=false`로5개 모두 완료했다.
각 복원 계산과 비교한 전체 반환 수치의 차이는 모두0이다(상대허용오차1e-8/절대1e-7).
근거는 `r5-independent-evaluation-v3/original-xml/R5-01`~`R5-05`의 입력 해시·native·comparison이다.
수치 일치는 XML 바이트 동일성이나 인게임 상호작용의 인증은 아니다.

최종물이 있는 H1 세 개는 모두 활성 ItemSet의 Ring1 원문이 고정 입력과 SHA까지 일치한다.
근거는 `r5-fixed-ring-xml-audit-v1.json`이다. 반지 준수만으로 공급 재투자 품질을 판정하지 않는다.

평가 실행기 첫 시도는 Windows 파이프 권한 오류, 다음 시도는 과거 R1 서버의 고정 도구
목록이 현재 추가 API를 거부해 시작하지 못했다. 실패 기록을 보존하고 정식 `pok.mcp`
진입점으로 평가 경로만 수정했다. 참가자 소스나 산출물은 수정하지 않았다.

## 설계 리비전과 실물 연결

개선판이 명시한 최종 설계 체크포인트3개를 바이트로 대조했다. 모두 material XML 해시가
실제 최종 XML과 일치했고, 참조한 material blob도 해당 해시에 맞았다. 각 current 근거의

## 남은 품질 검토

기준 H2 최종1의 명시된 `work/final-design.md`도 읽었다. 동결 소비가 폭발뿐 아니라
Shard Scavenger의 유탄 사용 횟수 복구로 이어지고, Flash의 제어/조건부 회복으로
소비되는 별도 자원 연결을 설명했다. 결정 파괴와 적 동결 소비를 구분했고, 내부 간격·
버프 만료·충전이 가득 찬 경우의 낭비·무적/빗나감·자연 재충전/회복의 대체 동작을 남겼다.
Second Wind의 회복이 충전 복구 사건 자체에서 발생한다고 확정하지 않고 관측 큐로 분리했다.

따라서 이 표본에서 “기준판은 단일 스킬만 고르고 개선판만 다단 회로를 구상했다”는
결론은 성립하지 않는다. 기준판은 자유 서술이라도 같은 의미의 운용·대가·미검증을
평가해야 한다. 기본 생명력3908/방어9680/회피14573과 개선판의3373/10903/9052는
서로 다른 구성/설정의 값이므로 더 큰 일부 수치만으로 전체 우열을 정하지 않는다.
기준판의 많은 능력치/저항 여유도 실전 완충과 투자 기회비용을 함께 검토할 대상이다.

## 결과 이후의 제품 수정 — 원래 실험과 분리

#211은 현재 제품의 계산·조립 공통 무결성 검사에서 잘못된 버프 stages 입력을
실제 config 경로와 함께 신고하도록 보완했다. 명시0·다른 단계 스킬·비활성 젬을 보존하고
유지율을 추정하지 않는다. 원래 개선판의 동결 소스와 참가자 답변은 그대로 남겼다.

#210 후속 prepare_pob_delivery는 해시로 지정한 XML을 직접 인코딩하거나 명시한 기존
코드와 정확히 대조한 뒤 불변 전달 파일을 만든다. 기본 반환은 파일 경로·참조이며
모델의 긴 코드 재전사를 요구하지 않는다. 진단/문서/공개 MCP 관련53검사는 통과했고
실제 최종5개 복사본도 XML과 정확히 대응하는 전달물을 생성했다.

명시 기존 코드의 정확 대조는 이 차이를 거부하며 자동 교체하지 않는다. XML을 직접
인코딩한 새 전달물은 원본 바이트와 일치한다. 근거 r5-delivery-real-files-v1/result.json.
