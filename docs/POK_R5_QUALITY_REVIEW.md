## 평가 범위

최종 응답이 명시한 5개 저장 PoB/XML, 대응 spec/validation, 최종 설계와 비교 보고서를

설명에 등장한 모든 역사적 대안과 모든 게임 상호작용을 독립 재검증한 것은 아니다.
계산·고정 반지 준수는 높은 확신, 선택 품질은 중간 확신, 실전 성립은 미확인이다.

아래 0~4는 R1과 같은 정성 기술 평가다. 설명 길이·도구 호출·고유 수·구조화 양식과
완료 도장을 가점으로 쓰지 않는다. 총점·군 평균·DPS 순위는 만들지 않는다.
최종 응답이 없는 시행은 미제출로 두며 품질0이나 중간 최선안으로 대체하지 않는다.

## 현재 해석과 남은 판정

이 표본에서 개선판만 복합 메커니즘이나 공동 재투자를 할 수 있었다는 주장은 지지되지
않는다. 기준 H1도 실제 다부위 재투자를 했고 기준 H2도 별도 자원 회로를 만들었다.
개선판3개는 실물/근거 리비전 연결을 남겼지만 입력 오진과 전달 오류를 막지는 못했다.
이는 기록 방식의 관측된 장점과 한계이며 일반 빌드 품질의 우열 증명은 아니다.

개선판은 최종 응답3개를 모두 complete로 냈고 기준판의 제출2개는 incomplete였다.
그러나 미제출·기한 초과와 모델 시작 전 실행 환경 오류를 구분해야 하며, 이 소표본으로
일반 완주율·속도·품질 효과를 확정하지 않는다. 호출/토큰/시간은 별도 비용 기록을 따른다.

사용자 PoB 검토·실전 체감은 아직 없다. 실행 환경 실패의 보충 시행은 별도 승인 없이
실행하지 않았다. 빌드 품질의 판정과 UI 배포 검증은 별개로 남으며, 이 초기 검토로
R5 완료·#188 해결·새 기본 경로 전환을 선언하지 않는다.

## #188 후속: 패시브 최적화 중단 경로 조사 (2026-11-02)

동결 로그에서 기준 H1 1회차의 optimize_tree는 두 단계 합계 5회 완료했다.
개선 H1 1회차 phase-1 item_288은 150초, 개선 H1 2회차 phase-1 item_436은
200초에 timed_out이었다. 두 종료 기록 모두 result_eligible=false이며 오류의
세부 정보가 비어 있어 이미 측정한 트리 후보를 회수할 수 없었다.

이 차이는 도구가 후보 탐색을 실제 선택으로 연결하지 못할 수 있는 구체적인
경로다. 다만 완료된 중간 측정이 있었는지는 과거 오류 기록만으로 알 수 없으며,
개선판은 이후 prepare_tree_variant로 수동 재검토도 했다. 따라서 「트리 재검토가
없었다」거나 「시간 초과가 품질 차이를 전부 설명한다」고 해석하지 않는다.

후속 수정은 측정이 끝난 정확한 BuildSpec과 수치, 입력 해시 및 목적을 중단
오류의 체크포인트에 보존한다. 아직 측정하지 않은 편집본에 앞선 수치를 붙이지
않으며 완료 결과·추천으로 승격하지 않는다. MCP 오류는 실패 상태를 유지하면서
get_execution_status 복구 경로를 제공한다. 영속 종료 기록도 같은 근거를 보존한다.

가짜 오라클 회귀에서 시간 초과·측정 전 중단·명시 취소·실제 MCP 오류 응답·
관리자 재시작 후 저장 근거 복구를 검사한다. 이 검증은 계산 신뢰성의 좁은 수정이며
빌드 품질 효과가 아니다. 실제 PoB의 짧은 30초 별도 진단은 복구 정보가 없었고,
등록된 native 자원도 없었다. 최초 측정 전 중단 경로를 배제할 수 없어 실패를
성공으로 세지 않는다. 이후 원래 150초 예산의 별도 진단을 수행했다.
원본 R5 참가자 이벤트나 최종 산출물은 수정하지 않는다.

다음 품질 판정은 복구 경로의 실동작을 확인한 뒤, 채택/미채택 후보와 최종
빌드의 패시브·장비·젬 선택을 같은 제약에서 비교해야 한다. #188은 미해결이다.

실제 PoB 후속 진단: 복사한 H1 입력/원래 150초 예산에서 timed_out을 유지하며
pok.interrupted-search.v1 응답으로 측정된 76노드 후보를 복구했다. CombinedDPS
7744.247277 / Life 2944 / EnergyShield 3200이다. 이는 최종 빌드의 개선 수치가
아니며 탐색 중간 후보의 계산값이다.
명시 취소 및 서버 관리자 재시작 후 복구 회귀도 통과했다. 관련 단위 50개와
저장 기록 포함 별도 14개, 수정 소스 2개 mypy와 Ruff가 통과했다.

별도 새 캐시 native 재계산 완료: cached=false, 저장된 모든 수치 차이 0,
할당/해제 노드 동일, dropped_items=[]다. 복구 정확성 검증이며 더 나은 최종
빌드의 증거는 아니다. 전체 단위 회귀를 진행한다.

### 선택 근거의 추가 관측

동결 도구 입력의 차이도 확인했다. 기준 H1 1회차는 처음 생명력·ES·마나 재생·
ES 재충전·DPS의 targets를 주었고, 후속 네 번에도 targets를 사용했다.
개선 H1 1회차의 단 한 번 최적화는 targets 없이 DPS 1 / ES 0.5 / 마나 재생 0.5의
가중치를 주었으며 열린 마음(59636)·마나 축복(61027)·몰입 상태(34233)를
required_anchors로 지정했다. 해당 노드의 의미는 당시 get_entry 응답
item_282/284/285에서 확인했다. 이것은 그 도구 호출에서의 고정이지 사용자
고정이나 전체 설계의 영구 잠금을 의미하지 않는다.

마지막 조립 입력에는 개선 H1 두 회 모두 세 노드가 남았고 기준 H1에는 앞의
두 노드만 남았다. 그러나 개선 H1 2회차는 required_anchors 없이 ES 4500과
DPS 100000의 targets를 사용했다. 따라서 「새 지침이 언제나 가중치만 쓰게
했다」거나 「새 도구가 세 노드를 강제했다」는 설명은 맞지 않는다. targets의
선정과 조건 충족 뒤 재배분, 세 노드 및 연결 경로의 대안 비교가 실제 채택에
어떻게 연결됐는지를 더 조사할 수 있다. 현재 관측만으로 세 노드의 가치나
어느 쪽 트리의 우수성을 단정하지 않는다. 총 tree_nodes 개수는 시작/전직 등도
포함할 수 있어 일반 패시브 예산과 같은 값으로 취급하지 않는다.

### #212: 후보 채택과 최종 선택의 목적 불일치

추가 코드 조사에서 Objective.score는 호출자의 targets를 우선하지만 최종 후보를
고르는 _better는 원시 가중 합만 사용함을 확인했다. 합성 사례에서 Life>=3000을
우선하도록 설정했을 때 Life2000/DPS20000→Life3000/DPS19000 후보의 점수는
+0.49995였으나 최종 비교는 이전 안을 골랐다. 이는 실제 PoB 측정 수치가 아니다.
하한·상한·달성 경계·목표 우선순위 회귀9개 중6개가 수정 전에 실패했다.

최종 비교에서도 기존에 달성한 경계를 먼저 보존하고 호출자가 정한 목표 순서대로
미충족 목표의 진전을 비교하도록 수정했다. 측정 없는 축을0으로 만들지 않으며
목표 충족 후 또는 비교 불가 시 기존 가중 가치/동률 처리를 유지한다.
수정 후 관련69개 회귀가 통과했다. 실제 PoB 및 전체 통합의 최종 리비전 검증은
별도로 남아 있다. 진행 중인 전량 통합은 이 후속 수정 전에 시작한 실행이다.

이는 PoK 최적화 도구 자체의 구체적인 정합성 결함이다. 이전/개선 경로가 공통으로
쓰던 함수이므로 A/B/C나 R5의 품질 차이를 단독으로 설명하지 않는다. 원시 가중 합과
그리디의 상대 변화율 차이, 전역 최적성 문제도 이 수정으로 해결했다고 하지 않는다.

최종 수정본 관련72단위 및 새 프로세스의 실제 PoB 트리 통합7개 통과.
CustomMods로 만든 명시적 계산 탐침의 피해/생명력 상충에서도 목표 충족 안을
선택했다. 이는 획득 가능한 장비나 실제 빌드 품질의 증명이 아니다. 이전에 시작한
전량 native157개도 통과했으며, 최종 전량 회귀와 CI 상태는 별도로 구분한다.

### 최종 선택의 노드 기여 진단

모델을 재실행하지 않고 최종 조립 입력3개를 복사해 baseline3회/제거안8회를
