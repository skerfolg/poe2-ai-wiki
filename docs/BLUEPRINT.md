# PoK 청사진 — 에이전트가 설계하고 엔진이 근거를 제공한다

상태: 2026-10-30 사용자 지시에 따른 전면 개정. 정책 방향은 채택,
구현 전환과 생성 품질 개선은 미검증이다.
기준: PR #149, `e7bd42993a4b51e7a1dcaeacc579573f6eeef846`.
진행: [Current Plan](CURRENT-PLAN.md). 단계별 개선·통과 기준: [ROADMAP](ROADMAP.md).
검증 계획·초기 감사·UI 계약: [재설계 검증](POK_REDESIGN_VALIDATION.md).

## 1. 제품과 성공 기준

PoK는 PoE2 빌드를 설계하는 에이전트에 지식·편집·측정·검증·기록 기능을 제공하는 엔진이다.
좋은 빌드를 선택하는 책임은 에이전트에 있으며, 엔진의 계산 성공이나 검사 통과가
선택의 우수성을 인증하지 않는다.

성공은 사용자의 목적에 맞는 실물 빌드의 품질과 그 근거로 판단한다.
메커니즘·장비·패시브·젬·유틸·자원·조작을 연결해서 설계하고,
핵심 선택으로 생긴 여유를 다른 부위에 재투자할 수 있어야 한다.
호출 수, 비교 수, 고유 수, 포인트 소진, 단일 DPS/EHP, 완료 도장은 대리 성공 기준이 아니다.

사용자 접점은 Codex/Claude와 별도 저장소의 pok-ui다.
두 접점 모두 같은 PoK 기능과 진단을 소비한다.
UI를 위한 PoB 해석·복원·계산 기능도 PoK 코어의 책임이다.

## 2. 개정 근거와 불확실성

기존 A/B/C 비교에서 사용자가 평가한 A의 상대적 우위와 B/C의 공동 재설계 부족을
문제로 채택한다. 하지만 각 1회의 결과로 원인을 확정하지 않는다.
현행 스킬도 발산과 구성 묶음 비교를 요구하므로, 문서에 창의성 원칙을 더 쓰는 것만으로
해결됐다고 보지 않는다.

검증할 원인: 절차/증빙 부담, 국소 최적화와 초기 선택 고착,
도구 정보 표현과 실행 결함, 목표의 지표 축소, 실행별 편차.
#149가 수정한 전달/격리/판정 결함의 효과는 새 정상 생성에서 검증해야 한다.
기존 C를 사후 수정판의 품질 시험으로 간주하지 않는다.

확정된 방향과 원인 가설을 구분한다. 구현 규모는 원인 분리 결과로 결정한다.
검증을 위해 만든 고정 단계·군별 도구 제한을 제품의 일반 생성 절차로 이식하지 않는다.

## 3. 책임과 경계

| 주체 | 책임 |
| --- | --- |
| 에이전트 | 목적 해석, 메커니즘 가설, 후보 발산, 구성 묶음 설계, 선택·기각, 기존 선택 재개방 |
| KB/인사이트 | 출처 있는 사실, 조건, 관계, 게임 내 확인과 미확인 구분 |
| PoB 연동 | 입력 복원·편집·계산·왕복, 버전·손실·미모델링 진단 |
| 결정적 엔진 | 조회·명시적 변경·비교·유한 탐색·제약 검사·근거 연결 |
| 스킬 | 설계를 돕는 질문과 상황별 안내. 특정 호출 순서를 생성의 유일한 해법으로 만들지 않음 |
| pok-ui | 작업 공간·리비전·표시·진행/취소·사용자 검토와 적용 |

유한 탐색 알고리즘도 후보 범위·목표·고정 조건에 종속된다.
결정적이라는 이유로 중립적이거나 전역 최적이라고 간주하지 않는다.
엔진이 선택한 후보는 에이전트가 다시 검토할 수 있어야 한다.

물리 구조는 [PROJECT_STRUCTURE](PROJECT_STRUCTURE.md)를 유지한다.
이번 개정으로 디렉터리·모듈 경계·저장 위치를 이동하지 않는다.
필요한 경계 변경은 근거와 UI 영향 및 이행 계획을 작성해 사용자와 합의한다.

## 4. 근거 의무와 설계 자유

강제할 것은 주장과 근거의 정합성이다:
계산 수치의 실제 입력/출처, 아이템·노드·젬의 조건, 변경 이후 근거의 유효 범위,
미검증 상호작용의 명시, 알려진 성립 불가 구성의 신고.

특정 최적화 도구를 호출했다는 사실을 좋은 설계의 증거로 삼지 않는다.
동등한 유효 근거 경로를 허용하며, 근거 없는 우회와 유효한 대체 경로를 구분한다.
판정기는 확인 가능한 사실과 누락 범위만 보고한다. 탐색의 충분성과 선택 가치는 별도 판단이다.

계산 불능·알려진 불법·정보 부족·미측정·조건부·탐색 미완료를 구분한다.
알 수 없다는 이유로 가능하다고 인증하지 않고, 알 수 없다는 이유만으로 불가능하다고 단정하지 않는다.

## 5. 도구 계약의 목표

기본 조회·복원·편집·계산·비교는 상위 생성 워크플로 없이 사용할 수 있어야 한다.
불완전한 초안을 탐색할 수 있어야 하며, 추천용 증빙 미완료를 기본 계산 불능과 혼동하지 않는다.
게임적으로 불가능한 조건이나 입력 손상은 탐색 중에도 명시적으로 드러낸다.

최적화 기능은 선택 가능한 유한 탐색이다. 다음 정보를 명확히 제공하는 방향으로 개정한다:
현재 문맥, 고정 조건, 실제 탐색 범위, 제외/실패/미지원 후보, 사용 목표,
실제 변경안, 측정 결과, 원본 복구 경로. 전체 최적성은 인증하지 않는다.

장비·트리·주얼·젬·config를 함께 바꾼 구성 묶음을 쉽게 만들고 비교할 수 있어야 한다.
마나·저항·속성·점유의 여유는 재투자 후보를 찾는 재료이며 자동으로 이득으로 계산하지 않는다.
모델이 가설 하나를 시험하는 입력·출력·대기 비용을 측정하고 줄인다.

응답은 판단에 필요한 요약과 진단을 먼저 제공하고 상세 근거는 회수 가능한 참조로 보존한다.
작은 응답이 누락을 숨기지 않게 실패/미측정/원문 접근 경로를 유지한다.
긴 실행은 진행·취소·기한·복구 결과를 구분한다. 이것은 목표 계약이며 현재 구현 보장이 아니다.

## 6. 설계·탐색·최종 추천

### 6.1 공통 설계 기록과 앵커

공통으로 고정할 것은 설계 정보의 형식·근거 의무·완료 조건이며 모든 빌드의 호출 순서가 아니다.
사용자마다 다음 행동을 지시하지 않아도 AI가 미해결 질문을 찾아 진행하도록 한다.
v2 설계 기록과 명시 변경/근거 검사는 구현됐으며, 실제 생성 품질 향상은 별도 검증한다.

| 앵커 구분 | 의미 | 재개방 |
| --- | --- | --- |
| 사용자 고정 조건 | 준비한 장비·원하는 전직·플레이 취향 등 | 사용자와 변경 협의 |
| 메커니즘 필수 조건 | 선택한 메커니즘의 공격·방어·자원 성립 조건 | 메커니즘 변경 또는 동등한 공급 수단으로 대체 |
| 잠정 구현 선택 | 필수 조건을 충족하는 현재 아이템·노드·젬 | 실측·대안에 따라 AI가 교체 가능 |
| 성능 후보 | 피해·방어·속도·편의 개선안 | 채택·기각·보류 |

필수 조건과 특정 공급자를 구분한다. 각 항목은 목적/의존 조건·근거와 검증 상태,
슬롯/포인트/자원/조작 비용·대체 후보·변경 시 재검토 대상을 가진다.
공격·방어로 나누어 읽되 자원/회복과 공유 슬롯을 함께 검토한다.
공격을 먼저 탐색할 수 있지만 방어·자원 성립 전 불변으로 고정하지 않는다.

설계 기록에는 사용자 목적, 메커니즘, 앵커, 후보/기각 이유, 미해결 질문과 판정 방법,
PoB/스펙 리비전과 근거의 연결을 보존한다.
정보의 소유 관계는 설계=이유/조건, build_spec·PoB=실제 구성,
측정=해당 입력에서의 관측, design.md·UI=사람이 읽는 표현으로 구분한다.
구조화된 설계 정본에서 일관된 문서를 생성하는 것을 목표로 하되,
기존 design.md 파서·build_spec·증빙을 조사해 R2에서 정본/파생과 이행을 확정한다.
같은 결정을 여러 곳에서 독립 편집하는 새 저장소를 추가하지 않는다.

### 6.2 AI가 진행하고 검사가 누락을 알리는 흐름

참고 흐름은 탐색→성립 검증→공격/방어/자원 앵커→성능 후보→초안→사용자 검토·개정이다.
필요하면 조기 계산·역행·재개방한다. 모든 앵커가 정해질 때까지 PoB 계산을 미루지 않는다.
성립 검증은 기존 KB/인사이트를 확인하고 부족·충돌 부분을 웹 조사하며,
미해결은 조건부 가설과 사용자 인게임 시험으로 연결한다. 자료 부재를 성립 증거로 삼지 않는다.

엔진은 저장된 조건/근거/리비전으로 감지 가능한 누락·오래된 근거·재검토 대상을 반환한다.
어떤 해법을 선택하고 다음에 무엇을 탐색할지는 AI의 판단이다.
감지 가능한 누락은 도구 검사의 후보로 두고, 감지할 수 없는 품질 판단은 AI/사용자에게 남긴다.
탐색 중 부족은 기록·신고하고 계산을 허용하되, 최종 추천에서 근거 없는 확정 주장을 막는다.
대화/자동 진행은 판단의 위임 범위만 다르며 기록과 근거 계약은 공유한다.
사용자는 취향·확정 조건 변경·인게임 관측·최종 체감을 판단하고,
AI는 검증 질문·대안·변경 영향·일상적인 진행을 먼저 제시한다.

### 6.3 추천과 호환

일반 생성의 순서와 후보 수를 고정하지 않는다.
에이전트는 목표를 이해하고 가설을 세워, 필요한 정보를 조회하고 실제 변경안을 측정하며
이득과 대가를 판단한다. 핵심 선택이 바뀌면 이전 장비·노드·젬 결정도 다시 열 수 있다.

설계 기록은 목적·가설·선택 이유·미해결 조건을 보존한다.
현재 design.md와 build_spec 및 근거 기록은 유지하며, 형식 개편은 소비자와 함께 이행한다.
문서 작성량이 설계 진척의 대리 지표가 되지 않게 한다.

최종 산출물에는 다음을 별개로 표시하는 방향으로 판정을 재설계한다:
입력/왕복 무결성, 게임 성립 조건, 측정과 미측정 범위, 탐색 범위, 사용자 목표에 대한 판단.
현재 ready/purpose 등의 스키마는 즉시 제거하지 않는다.
구버전 의미와 새 판정의 매핑을 먼저 정의하고 회귀 시험으로 전환한다.

## 7. pok-ui 연동

pok-ui는 별도 저장소로 계속 개발한다.
PoK가 PoB 및 게임 의미의 코어를 소유하고 UI는 작업 공간과 사용자 상호작용을 소유한다.
현재 UI의 XML 보존 편집과 정적 트리 렌더링을 즉시 철거하지 않는다.
UI에 게임 규칙·별도 계산기·강제 생성 절차를 복제하지 않는다.

2026-11-02 사용자 결정: 기존 `src/pok/pob` 소유를 유지하는 A안을 채택한다.
UI는 같은 코어에서 만든 독립 PoB worker·PoB snapshot·LuaJIT를 번들하고,
PoK 설치·연결·KB·AI 없이 수동 편집·계산을 제공한다. PoK/KB/생성 연결은 선택 기능이다.
독립 실행 경계와 배포 계약은 [승인한 설계](POK_UI_STANDALONE_BACKEND_PROPOSAL.md)를 따른다.
새 공용 패키지 분리는 채택하지 않았으며, 구현·배포·실제 동선 검증은 별도 완료해야 한다.

입력 식별·엔진/PoB 버전·진단을 결과와 연결하고 UI의 buildId/baseRevision 결박을 유지한다.
늦게 끝난 결과를 최신 편집본의 결과로 표시하지 않는다.
AI 제안은 사용자 검토 후 적용하며 원본·비활성 세트·미지 필드를 보존한다.

기존 MCP 도구의 제거/필수 필드 변경을 UI에 예고 없이 반영하지 않는다.
계약 변경 시 capability/schema 식별, 구버전 지원 범위, 합성 fixture,
엔진과 UI의 호환성 시험 및 이행 순서를 먼저 마련한다.
개발 엔진·번들 런타임·실제 로드 프로세스는 각각 식별한다.

## 8. 검증과 이행 순서

1. #149를 기준으로 실행 버전과 원자료를 고정한다. 병합 사실과 실제 프로세스 로드를 구분한다.
2. [원인 분리 계획](POK_REDESIGN_VALIDATION.md)에 따라 기본 기능/선택 최적화/현행 절차를 비교한다.
3. 결과에 따라 유지·수정·폐기할 계약과 구현을 정한다. 필요한 구조 변경을 별도 합의한다.
4. 대표 과제의 실물 품질·실행 신뢰성·UI 회귀를 확인한 후 기본 경로를 교체한다.

실험 실패와 timeout을 보존하고 중간 수정 전후를 같은 표본으로 합치지 않는다.
사용자 블라인드 평가와 축별 근거를 사용한다.
