## 1. 설계 문서란 무엇인가

- **빌드 생성의 1급 산출물**(D26). PoB 코드는 어떤 *상태*의 스냅샷이고, 설계 문서는 그 상태에 도달한 **판단·제약·가설의 기록**이다. 설계 루프(BLUEPRINT §10.0)는 이 문서를 반복 갱신하며 돈다.
- 저장 위치: `artifacts/builds/<build-id>/design.md` (+ `manifest.json`에 출처·버전·해시).
- 생성 파이프라인(에이전트·스킬)은 이 문서를 **입력으로 읽고**(§4 기계 가독 규칙), 갱신해 **출력으로 쓴다**.
- 미검증 가설 목록(§2-5)은 **P5 피드백 루프의 입력 형식**이다: 가설 목록 → 인게임 실험 → 결과 반영 → 문서 갱신.

## 2. 필수 섹션

순서는 권장이며, 섹션 제목 문구는 §4의 고정 제목만 지키면 된다.

### 2-1. 헤더 블록 (버전·갱신일·상태·운용 목표)

문서 최상단에 다음 4줄을 리스트로 둔다. §3 갱신 규약과 §4 기계 가독의 핵심이다.

> v6 실례:
> ```
> - 갱신일: 2026-07-31
> - 문서 버전: v6
> - 상태: 장비·정신력·로우라이프 점유 구조 확인 / 공격안 A의 화염폭풍 폐기 … / DPS·EHP 계산 전
> - 운용 목표: 일반 맵핑 1버튼, 보스전 최대 2버튼
> ```

`상태` 줄은 "무엇이 확인됐고 무엇이 남았는가"의 한 줄 요약 — 세션을 이어받는 에이전트가 가장 먼저 읽는 줄이다.

### 2-2. 고정 조건·설계 철학

- **고정 조건**: 이 빌드에서 협상 불가능한 것(전직·주력 스킬·핵심 유니크·운용 방식). 설계 루프 ①(컨셉)의 산출이자 이후 모든 판단의 전제.
- **설계 철학**: 판단이 갈릴 때 적용할 우선순위 규칙. 번호 목록으로.

> v6 실례: "점화·감전·주입·메타 발동의 불확실한 상호작용은 공격 배율에 선반영하지 않고 실험 항목으로 분리한다."

### 2-3. 제약 원장 (Constraint Ledger)

설계의 본체. 빌드를 깨뜨리는 것은 대개 DPS 부족이 아니라 **이산 제약 위반**이다. 각 제약은 (a) 규칙(수식·문구), (b) 현재 장부(표), (c) 여유분(headroom)을 함께 기록한다. 최소 4종:

| 제약 유형 | 내용 | v6 실례 |
|---|---|---|
| **포인트 예산** | 전직·패시브 포인트의 배타적 배분 | "전직 포인트 8개로 다음 네 묶음을 동시에 찍을 수 없다" → 마지막 2포인트가 분기 A/B를 강제 |
| **색상 장부** | 조건부 효과의 집계 조건(예: 보조 젬 색상) | 결정화된 면역 `빨강 보조 수 > 전체 장착 보조 수 ÷ 2` → 스킬별 색상 집계표 + "비빨강 2개 추가 시 6/12=50%로 실패" 경계 명시 |
| **점유(reservation)** | 자원 점유율과 상한·하한 경계 | `실제 성찬식 점유율 = 66% ÷ (1 + 총 점유 효율)` + "총 점유 효율 65% 초과 시 잔여 생명력 35%를 넘어 로우라이프가 풀림" |
| **자원 소진** | 되돌릴 수 없는 1회성 자원 | "목걸이에는 이미 성유가 할당되어 있으므로 … 목걸이 주입으로 해결할 수 없다" |
| **요구-수급 대응** | 계산·목표가 인용하는 요구 수치마다 **수급 장부**(어디서 얻는가) | 요구 수치를 인용한 계산은 그 수치의 소스 열거가 있어야 성립 — "기본값 → 요구값" **간극 명시**가 장부의 시작 (인게임 사후 부검에서 확립, 사용자 판정 2026-08-02) |
| **지속 가능성 경계** | 메커니즘의 부작용·비용이 가용 자원 안에서 버텨지는가 — `실효 = 원본 × (1−경감)` vs 가용 자원, 필요 경감 역산 | 자해·소모형 기제를 채택한 설계는 이 경계 계산이 **성립 조건 검증의 일부**다. 원본·경감·가용이 수치로 있으면 **측정 전에 상·하한부터 계산**한다 (블라인드 재현 검증에서 확립, 2026-08-02) |

빌드에 따라 소켓 수·Spirit 총량·젬 슬롯 등 제약 유형을 추가할 수 있다. 중요한 것은 **각 제약을 검증 가능한 규칙 + 현재 장부**로 적는 것 — "대충 된다"가 아니라 재계산 가능해야 한다(엔진 제약 검사기의 입력이 된다, D27).

**요구-수급 규율** (인게임 사후 부검에서 확립, 사용자 판정 2026-08-02): 계산식·목표 상태·예시에
등장하는 모든 **요구 수치**(상한 돌파형 스탯·목표 확률·자원 총량 등)는 그 수치를 만드는
**소스 열거(수급 장부)** 없이는 확정·잠정에 둘 수 없다. 수급안은 KB에서 열거한다(`search_kb`).
**가격 추산까지는 불요**(D19 — 요청 시만)지만, 수급 경로가 전무하거나 전부 고비용 경로뿐이면
그 사실 자체를 장부에 명기해 사용자가 자본 제약을 미리 판정하게 한다. 기본 수치와 요구 수치의
**간극**을 명시하는 것이 장부의 시작이다.

**가정 수치 등재 의무** (블라인드 재현 검증에서 확립, 2026-08-02 — 2차 회귀로 확장): **본문 서술·
수식·예시를 불문하고** 문서 어디에든 등장하는, 기본값·캡을 넘는 가정 수치는 **목표 상태로 등재한 뒤
장부화**한다 — "예시 속 수치"도 "산문 속 수치"도 스캔에서 빠지면 안 된다. "가능하면/높은" 같은
수식어가 붙은 목표는 반드시 **수치화**해 등재한다(수치 없는 목표는 장부화할 수 없다). 특히 미충족 시
운용 자체가 무너지는 **빌드 성립 조건**은 사전식 목표(D28)의 최상위군에 둔다 — 성립 조건이
미해결이면 하위 목표의 최적화는 무의미하다.

**성립 질문 규율** (블라인드 재현 검증에서 확립, 2026-08-02): 고정 조건의 **각 메커니즘마다**
"이것의 부작용·비용은 무엇이며, 현재 상태가 그것을 버티는가"를 명시적으로 묻는다. 부작용의
원본·경감·가용 자원이 수치로 존재하면 **측정 전에 상·하한 경계를 먼저 계산**한다(지속 가능성
경계 검사). "미측정"과 "측정 전에도 경계는 계산 가능"은 다르다 — 경계 계산을 기록하지 않은 채
측정 큐로만 미루는 것은 금지. 경계에서 나온 필요 경감·필요 자원은 요구-수급 장부로 넘긴다.

**축별 점유 장부** (블라인드 재현 검증에서 확립, 2026-08-02): 점유 장부는 자원 축마다
(생명력·정신력 등) **각각** 작성한다 — 한 축의 검증이 다른 축을 대신하지 않는다.
지속 스킬·보조 젬의 점유는 KB 수치(cost·reservation·additional_reservation)로 전수 합산한다.

**실측 이상 신호 반증 의무** (블라인드 재현 검증에서 확립, 2026-08-02): 검증 계산에서 나온
이상값(초과·음수·기대 불일치)을 "모델링 인공물"로 처리하려면 **반증**(해당 요소 제거 재실측 등)을
먼저 기록한다 — 반증 없는 인공물 결론은 실제 위반을 덮는다(반프록시 AD-8의 검증 버전).

**조회 실패의 원인 규명 의무** (2026-08-02 확립): 도구의 미매칭 판정(`UNKNOWN`·검색 0건)은
**"KB에 없다"의 증거가 아니라 "내 조회가 안 맞았다"의 증거**다. KB 갭으로 결론짓기 전에
① 도구가 제시한 근접 후보 확인 ② 정본 표기·명칭으로 재조회(한국어↔영문, 게임 내 표기)
③ 그래도 없으면 그때 갭으로 기록한다. 근거 없는 갭 단정은 실재하는 선택지를 설계에서
지워버린다 — 실증: 정본이 `+N to Spirit`인데 `+N to maximum Spirit`으로 조회해 UNKNOWN이
났고, 그것을 KB 갭으로 결론지어 갑옷 계획 전체가 검증 불가로 처리됐다.

### 2-4. 분기 관리

배타 제약이 강제하는 대안들을 **폐기하지 않고 병행 유지**한다. 각 분기는 명명(A/B…)하고, 전제·기대·열세 조건을 함께 적는다.

> v6 실례: "분기 A — 치명타 최고 화력형: 웃는 번제 / 분기 B — 점화·번개 주입형: 불꽃을 가져오는 자. … 불꽃을 가져오는 자 기획은 폐기하지 않는다."

분기 선택은 추측이 아니라 검증 항목 큐(§2-6)의 실측으로 결정한다.

### 2-5. 확정·잠정·미검증 3구분

KB 검증 라벨(BLUEPRINT §5)의 **설계 버전**. 문서 후반에 세 목록을 반드시 둔다:

- **확정** — 게임 내 확인됐거나 되돌리지 않을 결정. *(v6: "현재 구성에서 게임 내 점유 정보창으로 로우라이프 성립 확인")*
- **잠정** — 현재 최선이지만 실측·비교로 뒤집힐 수 있는 선택. *(v6: 불씨 5보조 세트, Forthcoming 휠)*
- **미검증** — 설계가 기대고 있으나 아직 확인 안 된 상호작용 = **가설**. *(v6: "붉은 보조 젬 우위에서 웃는 번제 자가 점화가 완전히 방지되는지")*

규율: 미검증 항목은 공격 배율·방어 계산에 **선반영하지 않는다**(v6 설계 철학 6). 확정으로 승격은 게임 내 확인 또는 PoB 실측 근거가 있을 때만.

### 2-6. 검증 항목 큐 (다음 결정 순서)

미검증 가설과 잠정 선택을 **실험 가능한 단위로, 결정 의존 순서대로** 번호 목록화한다. 앞 항목의 결과가 뒤 항목의 전제가 되도록 정렬한다.

> v6 실례: "1. 공격안 A의 구형 번개 보조 세트를 실제 스킬 패널에 장착해 `빨강 6 / 파랑 3 / 초록 1`이 성립하는지 확인 → 2. 결정화된 면역의 점화 면역 표시와 … 확인 → …" (총 16항목)

이 큐가 곧 다음 세션·다음 인게임 플레이의 작업 목록이며, P5 피드백 루프의 실험 계획이다.

### 2-7. 참고 자료·증거 링크

판단의 근거가 된 외부 소스(poe2db·wiki·포럼·공식 자료) 링크 목록. KB에 없는 근거를 문서가 자체 보유하게 해, 나중에 KB 수록 후보 추출(KI-3)의 원천이 된다.

## 3. 갱신 규약

0. **설계 문서는 흐름(설계 루프 실행)의 출력물로만 갱신한다** (사용자 확정 2026-08-02).
   에이전트가 루프 밖에서 수동 편집하지 않는다 — 프로젝트의 목표는 빌드 완성이 아니라
   **빌드를 생성시키는 흐름의 완성**이며, 손으로 고친 문서는 흐름이 그 상태에 도달할 수
   있다는 증거가 되지 못한다. 도메인 지식·인게임 피드백은 **KB·규칙(이 문서)으로만**
   진입시키고, 그것이 설계 문서에 반영되는 일은 루프가 해낸다 — 루프가 반영하지 못하면
   그것이 곧 흐름의 결함 신호다.
1. **버전은 단조 증가**(v1, v2, …). 문서를 실질 수정하면 버전과 갱신일을 올린다. 이전 버전 파일을 남길 필요는 없다(git이 이력 보유).
2. **상태 줄 갱신 의무** — 버전을 올릴 때 `상태:` 줄을 현재 사실로 다시 쓴다.
3. **폐기는 삭제가 아니라 기록** — 기각된 안은 사유와 함께 남긴다. *(v6: "#### 폐기: CoEA 화염폭풍" 섹션이 5개 사유를 명기)* 같은 실수를 반복하지 않는 것이 목적.
4. **정정은 명시** — 이전 버전의 오류를 고칠 때 "정정"임을 표기한다. *(v6: "5.2 CoEA 품질에 대한 정정", "중요한 정정: 앗지리의 성찬식은 … 파란 보조 젬이다")*
5. 3구분 이동(미검증→확정 등)은 근거(게임 내 확인·PoB 실측·소스 링크)와 함께.

## 4. 기계 가독 규칙 (최소 계약)

생성 파이프라인이 design.md를 파싱할 때 기대는 것은 아래가 전부다. **이 이상의 스키마화(YAML frontmatter·JSON 필드 강제)는 하지 않는다** — 설계 문서는 사람과 에이전트가 대화하며 쓰는 문서이고, v6이 증명하듯 마크다운+표로 충분하다.

1. **헤더 4줄**: 문서 상단 리스트에 `갱신일:` `문서 버전:` `상태:` `운용 목표:` 로 시작하는 줄이 각 1개.
2. **고정 섹션 제목** (수준 무관, 포함 매칭):
