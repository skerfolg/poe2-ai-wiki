# 생성·탐색 개정안과 최소 반증 평가

2026-11-04. 상태: 검토 결과에 따른 구체 제안. 구현·시험 실행 승인 또는 품질 개선
인증이 아니다. 근거는 [조사 기록](POK_GENERATION_SEARCH_REVIEW_FINDINGS.md).
코드 기준은 PR156의70e5d4a, 최초 A/B/C와 후속 시험의 버전을 구분한다.

## 결론과 선택한 방향

기존의 ‘에이전트가 판단하고 엔진이 사실·편집·측정·기록을 제공한다’는 경계를 유지한다.
전면 재작성이나 도구 분해 자체가 해결책이라는 증거는 없다. 공동 재투자는 H1에서
가능했고, 최신 지침을 받은 H2에서도 핵심 공급의 불확실성을 마지막 선택에 충분히
반영하지 못했다. 따라서 우선 바꿀 단위는 **현재 선택을 재검토하는 판단 방식**이다.
동시에 자동 후보집합의 누락과 구체화 한계는 독립적으로 측정한다.

규칙을 늘리기 전에 다음 세 질문에 답하도록 기존 설계 기록과 도구를 사용한다.

1. 이 빌드가 사용자 목적을 달성하려면 어떤 가정이 참이어야 하는가?
2. 새 관측은 어느 가정을 얼마나 약화시키며, 그 가정 없이도 어떤 기능이 남는가?
3. 현재 구현을 유지할 때와 공급/소비/자원 배분을 바꿀 때의 전체 손익은 무엇인가?

모든 변경에 전체 빌드 재탐색을 요구하지 않는다. 결론을 바꿀 수 있는 가정부터 다룬다.
그 중요도와 대안의 가치는 에이전트 판단으로 남기며, 코드가 어휘나 임의 임계값으로
빌드의 좋고 나쁨을 판정하게 하지 않는다.

않는다. 반면 선언한 의존 참조·입력 결박·변경 전파는 감지 가능하므로 기존 검사로
확인한다. 실험에서 이 경로 자체가 누락을 놓칠 때만 작은 결정적 진단을 추가한다.

## 생성 접근 제안 — 기존 계약 안에서 시험

### 가정에서 다음 행동으로 연결

각 핵심 선택에는 이를 지탱하는 가정, 현재 근거, 실패 시 영향을 기존 condition,
depends_on, evidence, question 필드로 표현한다. 새 스키마를 먼저 만들지 않는다.
‘실패하면 상시라고 쓰지 않는다’는 보고 기준과 ‘실패하면 이 선택을 다시 비교한다’는
판단 기준을 구분한다. 사용자 고정은 보호하되 AI가 고른 공급자를 고정으로 승격하지 않는다.

증거가 약해지면 아래 중 목적에 맞는 행동을 선택하고 이유를 남긴다.

- 공급을 보강한 완성 구성과 그에 따른 비용·방어 손실을 비교한다.
- 소비의 의존도를 낮추거나 다른 주력 구조로 바꾼 구성을 비교한다.
- 미확인 효과 없이도 목적을 충족하면 잠정 채택하되 그 효과를 기본 성과에 넣지 않는다.
- 불확실성이 선택을 뒤집을 정도면 비교 경계와 필요한 사용자 관측을 제시한다.

선택 개수나 호출 순서를 강제하지 않는다. 핵심 가정이 깨졌는데도 변경 없이 설명만
늘어나는지를 평가한다. 예측 불가능한 게임 상호작용을 임의 가동률로 메우지 않는다.

### 부품의 단독 점수와 완성 조합 구분

새 슬롯·포인트·자원·경로를 여는 부품은 그 공급을 사용하는 동반 구성까지 제안한다.
단독 측정은 해당 입력에서의 관측으로 보존하되 완성 조합의 기각 근거로 확대하지 않는다.
반대로 추가 부품 비용을 숨겨 묶음이 항상 낫다고 주장하지 않는다. 묶음의 투자와
조작·회복 대가까지 맞춰 비교하며, 범위를 맞출 수 없으면 우월성 주장을 제한한다.

### 발견과 선택 분리

PoK는 후보를 찾고 구체화하는 수단이다. 최적화 도구의 기본 후보만을 전체 세계로
간주하지 않는다. 다만 모든 고유를 무조건 조사하는 새 절차도 만들지 않는다. 사용자
목적의 병목을 바꿀 수 있는 효과를 기준으로 검색·후보 확장을 판단한다.
고유 개수, 비싼 아이템 채택률, 조회 수 자체는 품질 지표가 아니다.

## 최소 평가 명세 — 실행하지 않은 제안

### 0. 모델 호출 없는 사전 확인

기존 H2 기록으로 가정-선택 의존을 기존 필드에 표현할 수 있는지 확인한다. 선언된
근거 변경이 관련 선택만 재검토 대상으로 만드는지 기존 검사로 확인한다. 이 단계는
모델의 판단 개선이나 빌드 품질 검사가 아니며 새로운 UI/API를 먼저 요구하지 않는다.

### 1. 판단 방식 비교: 4회, 총 상한3시간

서로 다른 미공개 과제2개 × 기존 지침/제안 지침 각1회, 회당45분 상한을 제안한다.
새 실행 예산이며 과거12회 승인을 재사용하지 않는다. 반복1회이므로 통계적 우월성이
아닌 다음 수정 위치를 결정하는 탐색 평가다. 선택된 운영 모델과 추론 설정을 네 실행에
동일하게 고정하고 버전·전체 입력·제공된 근거·실제 산출물을 보존한다.

과제는 결과를 열람하기 전에 다음 구조로 선정·봉인한다.

- T1: 슬롯/자원/연결 비용을 바꾸는 선택이 있어 단독 교체와 완성 조합 평가가 다른
  문제. Voices/아이스샷과 동일 부품·주력·정답을 사용하지 않는다.
- T2: 사건 피해가 높아도 공급/소비/회복 또는 조작 조건 때문에 목표 달성이 달라지는
  문제. 기존 H2의 동결 석궁을 재사용하지 않는다.

구체 재료·효과·획득 제약은 두 정책 모두에 동일하게 제공하되 완성 조합·순위·참조
최종 수치는 숨긴다. 조합 구성은 에이전트가 한다. 과제 선정자는 참조를 볼 수 있지만
실행 에이전트와 최초 기술 평가자는 정책 라벨·참조 정답을 보지 않는다. 이를 분리할
운영 여건이 없으면 비맹검 한계를 명시하며 ‘미공개’ 평가라고 부르지 않는다.

두 정책의 차이는 본 문서의 가정 재검토 안내뿐이다. 같은 고정 코어·KB·PoB·도구,
동일 목표·자원 한도·최종 제출 계약을 쓴다. 새 코어 수정까지 섞으면 원인을 분리할 수 없다.
소스/컨셉/조달 조건이 맞는 과제와 참조를 확보하지 못하면 실행하지 않고 선정 갭을 보고한다.

평가 항목은 실제 산출물과 명시 근거에 근거한다.

| 판별 질문 | 성공에 필요한 증거 | 반증/실패 |
|---|---|---|
| 필요한 동반 투자를 스스로 만들었는가 | 실제 묶음 입력·비교와 동일 투자 범위의 손익 | 재료를 받았는데도 단독 점수로 기각하거나 답안이 제공돼야 구성 |
| 불리한 관측을 선택에 반영했는가 | 유지/변경 결정과 실제 대안, 조건별 결과 | 경고·문서만 늘고 핵심 의존은 같은 상태 |
| 사용자 목적에 더 적합한가 | 자원/방어/조작/성능의 대가와 실패 시 기능을 함께 검토한 PoB | 조건부 사건 수치만 증가하거나 실물에서 핵심 변경 누락 |
| 도구 비용이 중요한 탐색을 밀어냈는가 | 공개 호출 시각·실패·결과 회수와 미완료 작업 연결 | 호출 수나 토큰 감소만으로 품질 개선 주장 |

좋은 설명만으로 통과하지 않는다. 과제의 하드 제약·실물·무결성이 우선이고, 그 뒤
사용자 목적에 대한 선택을 본다. 실전 미확인은 별도로 표시한다. 선호가 엇갈리면
단일 합산 점수로 감추지 말고 손익 차이를 보고한다. 평가자는 제안 정책에 유리한
새 채점 기준을 결과 열람 후 추가하지 않는다.

### 2. 발견 경로 비교: 조건부 추가4회, 상한3시간

1단계에서 재료가 주어지면 목표에 맞는 조합을 만들 수 있었을 때만 시행을 제안한다.
동일 사실 범위에 접근할 수 있게 하되 선별 재료 목록을 제거한 두 정책×두 과제로
발견에서 선택까지 확인한다. 앞 실행의 답이나 대화는 전달하지 않는다. 동일 과제의
재사용이므로 독립 일반화 검증이 아닌 발견 조건의 진단이며 운영자 학습의 한계도 남긴다.

재료 제공에서 실패하면 검색 도구를 계속 늘리지 않고 판단/조합 가설을 수정한다.
제공에서는 성공하고 자율 탐색에서 실패하면 조회·후보 범위·구체화 경로를 조사한다.
양쪽 모두 성공해도 일반화 입증은 아니며 별도 신규 과제 반복이 필요하다. 그 후속
캠페인은 이번 최소 계획의 자동 연장 대상이 아니다. 최대 제안은8회/6시간이고,
2026-11-05 사용자 승인: 판단4회와 성과 조건 충족 시 발견4회, 총8회/6시간 이내다.

인프라 실패는 품질0점으로 바꾸지 않는다. 실행 중간에 좋은 답이 나올 때까지 같은
정책만 재시도하지 않는다. 실패 기록을 보존하고 재시험 필요성과 범위를 별도 결정한다.

## 청사진에 반영할 구체안

대상: BLUEPRINT §2, §5, §6.1–6.3, §8. 기존 책임·저장 위치·UI 경계를 유지한다.

- §2: A/B/C의 도구 비용, H1의 공동 재투자 가능, H2의 정보 전달 후 재검토 부족,
  아이스샷의 표현 손실을 분리한 근거표를 연결한다. 단일 원인 서술을 피한다.
- §5: 탐색 범위 밖 후보와 구체화 가능한 대안을 구분한다. 후보집합 확대는 측정
  지원 범위를 투명하게 만드는 기능이며 선택 개선은 별도로 평가한다고 명시한다.
- §6.1–6.2: 검증 질문에 관측 방법뿐 아니라 영향을 받는 선택·재검토 조건을 연결한다.
  기존 기록으로 표현 가능한지 먼저 확인하고 의미 판단을 엔진에 이식하지 않는다.
- §6.3: 미검증 공개만으로 목적 적합성을 인정하지 않는다. 핵심 효과 없이 남는
  기능과 경쟁 대안의 손익을 선택 이유에 포함한다. 특정 고유·구조 채택을 강제하지 않는다.
- §8: 자료 제공 조건과 자율 탐색 조건을 나누고 기존 답을 본 사례를 회귀로만 사용한다.

| S2 | 제안 지침을 평가용으로 고정 | 기존 지침과의 차이, 과제/자료/채점/예산 봉인. 제품 기본 지침 즉시 교체 금지 |
| S3 | 최소 판단 평가 | 4회 이하 결과와 실패 원장. 효과 없으면 가설 수정, 자동 기능 누적 금지 |
| S4 | 조건부 발견 평가 | S3가 판단 가능성을 보였을 때만 추가4회 이하. 발견/구체화 결함 분리 |
| S5 | 확인된 병목만 수정 | 엔진은 결정적 진단·표현·실행 결함, 스킬은 판단 안내. 해당 회귀 최소 검사 |
| S6 | 일반화·제품 채택 판단 | 별도 미공개 과제 반복 계획과 사용자 품질 검토 후 기본 전환 여부 결정 |

R6 UI 기능 작업은 다른 세션에 남긴다. 검토 결과가 기존 API 의미·판정 범위를 바꾸면
변경 계약을 먼저 전달하고 UI에 별도 게임 판단 로직을 만들지 않는다. PR156의 계산·
복원 교정은 이 새 접근의 품질 효과로 소급하지 않는다. 병합은 사용자가 수행한다.

## 이 검토에서 하지 않은 것

새 솔버·강제 후보 수·비싼 고유 채택 규칙·참고 빌드 맞춤 확장, 신규 모델 호출,
전체 단위/통합 검사, 게임 실험, UI 변경, PR 병합을 수행하지 않았다.
본 문서 완료는 구현 또는 빌드 품질 해결을 뜻하지 않는다.


## 사용자 확정 방향 — 메커니즘 검증과 앵커 선택

2026-11-05 후속 논의. 기존4회 동결 평가에 소급 적용하지 않는 차기 생성 흐름 요구다.

기본 흐름은 메커니즘 탐색 → 성립 검토 → 앵커 설정 → 앵커 기반 초안 → 비판/피드백
개선이다. 각 단계 안의 조회/계산 순서를 불필요하게 고정하지 않고, 검토 결과에 따라
이전 선택을 재개방할 수 있다.

### 메커니즘 검증과 실험 승인

1. 먼저 PoK KB/인사이트로 규칙과 기존 검증을 조사한다.
2. 다음으로 핵심 기재 사이의 실제 연결이 유효한지 웹에서 확인한다. 부품 각각의
   존재와 문구만으로 전체 연계가 확인됐다고 하지 않는다. 출처의 패치와 적용 범위를 기록한다.
3. 웹에서도 핵심 연결의 근거를 찾지 못하면 이 운용 정책에서는 실험적 메커니즘으로
   분류한다. 검색 실패는 불가능의 증명이 아니지만 자율 확정의 근거도 아니다.
4. 충분한 근거가 있으면 자율 진행한다. 실험적 메커니즘은 가정할 연결과 실패 영향,
   현재 확인된 부분을 구체적으로 제시하고 사용자 승인을 요청한다. 승인에 의존하는
   구현은 답변 전 확정하지 않는다. 그 외 독립 작업은 계속할 수 있다.
5. 승인되면 승인한 연결이 성립한다는 전제로 앵커 선정·초안·최적화를 진행한다.
   반복해서 같은 승인을 요구하거나 인게임 미확인만으로 진행을 막지 않는다.
   기록에는 ‘사용자 승인 성립 가정’을 유지하며 검증 완료로 승격하지 않는다.
   PoB가 재현하지 못하는 효과와 대리 계산은 기존 추산 계약을 따른다.

사용자 승인은 명시한 게임 상호작용 가정의 사용 승인이다. 포인트·슬롯·점유·장비
획득 조건까지 면제하거나 다른 미확인 연결의 승인으로 확대하지 않는다.

### 앵커 선정과 제약 안에서의 선택

앵커 후보와 선택 이유의 추론은 에이전트가 수행한다. PoK를 쓰지 않는 모델도 이미
유효한 앵커 후보를 제시했으므로 새 앵커 선정 솔버가 필요하다고 전제하지 않는다.
PoK는 사실 조회, 실제 구현, 비용/제약 계산, 비교 근거 보존을 제공한다.

후보 앵커를 전부 동시에 채택할 수 있다고 가정하지 않는다. 후보를 먼저 정리한 뒤
연결 경로를 포함한 패시브 비용, 공유 슬롯, 점유, 능력치, 자원/회복 및 배타 조건을
계산한다. 충돌하면 경쟁하는 앵커/묶음을 각각 구현해 공격·방어·자원·조작의 손익을
비교한다. 공급자를 바꾸어 같은 필요조건을 충족하는 대안도 포함한다.

사용자와 조율하는 흐름에서는 이 비교를 사용자의 선택 자료로 제공한다. 완전 자율
흐름에서는 사용자 목적과 고정 조건 안의 일반 선택을 에이전트가 수행한다. 사용자
고정을 포기해야 하거나, 실제 선호가 없어 우열을 결정할 수 없을 때 구체적인 대안을
제시하고 사용자 판단을 요청한다. 막연히 ‘포인트 부족’이라고 되돌려 보내지 않는다.

실험 승인 전후의 상태나 명시 비용/충돌처럼 도구가 확인 가능한 부분은 기존 계약의
표현/검사 지점을 먼저 확인한다. 새로운 규율을 문서에만 적어 구현 완료로 주장하지 않는다.
이 절은 차기 실행 요구이며 아직 제품 강제 지점/새 모델 효과를 검증한 것은 아니다.


## 다음 검증 범위 — 1~3단계 사용자 검토 관문

사용자 지시: 우선 메커니즘 탐색·성립 검토·앵커 설정까지만 제대로 수행하는지 확인한다.
사용자가 설계와 앵커를 검토해 만족스럽다고 판단한 뒤4단계 PoB 생성으로 진행한다.
이 검증을 위해 PoB 생성/조립이나 새 대규모 모델 캠페인을 먼저 시작하지 않는다.

대상 브리프는 **젬링 리저네어·활 두 조건만 고정**이다. 기존 T2를 자동 재사용하거나 예전 대화의
보유 장비/취향을 새 요청의 고정 조건으로 추정하지 않는다.

검토 산출물은 다음을 포함한다.

- 사용자 목적·고정 조건·열린 선택과 투자/조작 선호.
- 후보 메커니즘의 실제 작동 흐름, 성장 요인, 비용/약점과 선택·기각 근거.
- PoK 조사와 웹 핵심 연계 확인의 출처/버전/근거 범위. 미확인 핵심 연계는 실험적
  메커니즘으로 제시하고 승인받은 성립 가정과 구분한다.
- 공격·방어·자원의 성립 필요조건과 각각의 현재 공급 수단. 필요조건과 특정 장비를
  혼동하지 않는다. 사용자 고정/필수 조건/잠정 구현/성능 후보를 표시한다.
- 각 앵커의 역할·선행 조건·공유 자원·대안·기각/재검토 조건. 고유·보조·주얼도
  효과와 기회비용에 따라 후보를 검토하며 채택 개수를 성공 기준으로 만들지 않는다.
- 알려진 포인트·슬롯·점유·배타 충돌과 비교할 대안. 패시브 연결 비용/전체 예산을
  아직 계산하지 않았다면 확인된 것처럼 표시하지 않는다. 설계 검토를 위한 알려진
  제약 확인과4단계의 실제 PoB 조립·최적화를 구분한다.

현재 성공 기준은 실제 빌드 성능이 아니라, 사용자가 타당한 메커니즘과 만족스러운
앵커를 검토하고 선택할 수 있는 설계가 나왔는가다. 기존 전체 품질 개선 실패 판정은
그대로 보존하며 이 작은 검증의 성공으로 뒤집지 않는다.

## 자율 실행 구현과 실제 검증 (사용자 재확인 2026-11-05)

수동 도구 조합으로 후보를 제안한 이전 결과는 자동화 구조 검증이 아니며 참고 조사로만
보존한다. 이번 작업은 기존 skills/build-generation 경계에서 1~5단계 실행·저장·재개·
실험 승인·피드백 루프를 구현하고, 새 모델 세션에 요구문만 주어 1~3단계를 검증한다.
이전 수동 후보·원본 아이스샷·과거 정답을 새 실행에 주입하지 않는다.

- A1: 실행 계약·정본 참조·단계 표면·명시 승인/피드백 재개 구현.
- A2: 추상 앵커 방지, 실험 승인 범위/변경 만료, 단계 4 진입 차단 최소 검사.
- A3: 젬링·활 새 요구를 실제 PoK+웹 도구로 실행. 후보/앵커는 모델이 결정.
- A4: 메커니즘, 상세 필수/선택 앵커, 공급 효과·선정 이유·대안·제약·미확인 보고.
  사용자 검토를 기다리고 PoB 생성은 시작하지 않는다.

앵커는 필수 고유·일반 장비 조건, 스킬·보조 링크, 패시브 이름/ID·효과까지 구체화한다.
각 앵커의 인과·비용·선행·충돌·대안·재검토 조건을 기록하고 공격/방어/자원과 선택적
DPS/EHP/사용감 개선을 구분한다. 고유/주얼 개수 할당량은 두지 않되 해당 부류를
검토하지 않고 완료하는 것은 막는다. 도구는 선언 누락과 실제 호출/참조만 검사하며
문장 해석·메커니즘 진실성·좋은 빌드 여부를 형식만으로 인증하지 않는다.
