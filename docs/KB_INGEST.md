## 2. 파이프라인 (수동 트리거, 패치 시)

```
① fetch     계획 주도 수집 → 원시를 데이터 repo에 커밋·push (§3 체크포인트)
② parse     소스별 파서: 원시 → 소스 스키마 그대로의 중간 레코드 (가공 최소, var/에 캐시)
③ match     소스 간 엔티티 매칭 — 키 = (type, 영문명), 예외는 수동 매핑 테이블(정본 커밋)
④ merge     필드 단위 D8 우선순위 병합 (카탈로그=poe2db·계산=PoB·서술=wiki)
            충돌 → CONTRADICTED 라벨 + 리포트 (조용한 덮어쓰기 금지)
⑤ validate  knowledge/schema/ 전체 검증 (envelope·조건 expr·관계 무결성)
⑥ review    ★ 사람 게이트 (KI-3): 리포트 → 일괄승인, 충돌·매칭실패만 개별
⑦ commit    knowledge/ 커밋 (패치=commit, 시즌=tag) + manifest에 데이터 repo commit 해시 기록
⑧ narrative 서술 재작성 (KI-2: 함께 진행) — poewiki 원문 → 자체 재작성 → knowledge/wiki/
            사람+에이전트 공동 작업이라 ①~⑦과 달리 벌크 자동화 불가, 커밋은 동일 게이트
```

- **②③④ 분리 원칙**: 파서(소스 취약성)와 병합(정책)을 섞지 않는다. poe2db HTML이 바뀌면 ②만 수정.
- **멱등**: ①만 네트워크. ②~⑤는 원시에서 결정적 재실행(파서 수정 시 재스크래핑 불필요).
- **매칭 실패 = 에러가 아니라 리포트 항목** — 신규 엔티티인지 누락인지 ⑥에서 사람이 판별.
- 코드 위치: `src/pok/kb/ingest/` (fetch/·parsers/·match·merge·report — 기존 경계 내).

## 3. 체크포인트 — 멀티 PC·분담 대응 (KI-4)

**원리: 진행 상태 자체가 데이터 repo의 일부 → `git pull` = 체크포인트 복원.**

```
artifacts/ingest-raw/<patch>/          # = 데이터 repo 체크아웃
├── fetch-plan.json                    # 수집 계획 = 전체 항목 목록 (먼저 확정·커밋)
├── fetch-status.<source>.json         # 항목별 pending|fetched(+해시)|failed(+사유)
└── <source>/…                         # 원시 파일 (append-only)
```

- **재개**: 어느 PC든 pull → `pending`/`failed`만 이어서 수집. 완료 항목은 해시 확인 후 스킵(멱등).
- **분담**: 모든 산출이 서로 다른 경로에 append-only → git 충돌이 구조적으로 없음. status는 소스별 파일 분리로 동시수정 회피. 분담 단위 = 소스별 또는 타입별.
- **fetch 이후 단계는 체크포인트 불필요** — 원시에서 결정적으로 재실행되는 오프라인 연산(실패 시 그냥 재실행).
- **큐레이션(사람 편집)의 체크포인트는 git 그 자체** — `knowledge/`는 본 repo 커밋이 곧 체크포인트.

## 4. 완전성 기준 — 8중 혼합 (KI-5)

**"전체를 다 모았다" = 아래 여덟이 전부 통과** (각자 사각지대가 있어 단일 기준 금지):

| # | 기준 | 잡아내는 것 |
|---|---|---|
| ① | **계획 대비 완수** — fetch-plan의 모든 항목이 fetched (pending=0, failed=0) | 수집하다 만 것 |
| ② | **소스 교차 대사** — PoB 덤프(게임파일 유래, 정확한 전수)와 poe2db 수집분 상호 매칭, 한쪽에만 있으면 명시적 누락 리포트 | 스크래핑 누락·목록 페이지가 안 보여준 항목 |
| ③ | **개수 불변량** — poe2db 카테고리 표시 개수 vs 실수집 / PoB 트리 JSON 노드 수 vs 수집 노드 수 | 파서가 조용히 흘린 항목 |
| ④ | **KB 참조 무결성** — 모든 relations.target·satisfiable_by가 실존 id (⑤validate) | 수집됐지만 정형화에서 빠진 것 |
| ⑤ | **패치 간 델타 sanity** — "스킬 512→518(+6)"은 정상, "512→460"은 스크래퍼 고장 신호. 승인 리포트에 타입별 델타 표기 | 도구 고장을 데이터 변화로 오인 |
| ⑥ | **교차 일관성** — 같은 key인데 **이름·값·효과가 다른** 항목 리포트 + 단독 항목 **양방향** + 한 소스 안의 중복 key 충돌 | 존재는 맞는데 **내용이 틀린** 레코드 |
| ⑦ | **정보량 하한** — 수록 대상인데 실질 정보(stats/mods/효과)가 빈 레코드 리포트 | 구조·그래픽 노드가 지식인 척 섞이는 것 |
| ⑧ | **획득 경로 커버리지** — 타입별 "어떻게 얻는가" 보유 비율. 낮으면 수집 누락 신호 | 조건 판단 불가 상태(RC1)로 KB가 자라는 것 |

**기준 ②의 재해석 (KI-8)**: PoB 전수 목록은 "게임의 진실"이 아니라 **"PoB가 아는 것"**이다 — PoB에도 PoE1 잔재가 남아 있다. 교차 대사는 누락 *감지*용이며, 존재 *판정*은 §4-1의 구현 게이트(획득 증거 우선)가 한다.

### 4-0. ⑥⑦⑧ — 왜 추가했고 어떻게 도는가 (2026-07-29)

**추가 계기**: 사용자가 하루에 데이터 결함 3건을 연속으로 잡아냈고 **셋 다 ①~⑤를 통과한 뒤**였다.
마스터리 368(정보량 0인 배경 그래픽을 수록) · 성유 부여방법 누락(패시브 884의 획득 경로 부재) ·
소스 간 이름 불일치 22(Arsonist↔Pyromancer). 공통 원인은 **한 소스만 기준으로 순회하고,
교차 검증을 "존재 여부"에만 쓴 것** — ②는 "양쪽에 있나"만 물었지 "같은 걸 말하나"는 묻지 않았다.

- **구현**: `src/pok/kb/ingest/verify.py` 하나를 젬·트리·유니크가 공유한다. 각 모듈은 자기 소스를
  `SourceEntity`(key·name·substance·acquisition·facts·sets)로 접어 넘기기만 한다.
- **출력**: 각 카테고리 리포트의 `verification` 블록 (`6_cross_source`/`7_substance_floor`/`8_acquisition_coverage`),
  기존과 같은 위치(`artifacts/ingest-raw/<patch>/…/report.json` = 데이터 repo).
- **검증기는 판정하지 않는다** — 세고 표본을 남길 뿐, 항목을 버리거나 고치지 않는다. 수정은 KI-3 게이트(사람)에서.
- **집합 필드는 방향별 차집합으로 본다** — 문자열로 이어 붙여 비교하면 표기 차이만으로 전건 불일치가 된다
  (실측: 젬 태그 통짜 비교 931/931 "불일치", 트리 stats 마크업 미정규화 4,255/4,914 "불일치").
- **중복 key 충돌**이 ⑥에 포함된 이유: 같은 key가 한 소스에 두 번 나오면 뒤 항목이 조용히 버려져
  교차 대사가 영원히 보지 못한다. 실측으로 유니크 재배판 48건의 깨진 `base_type`이 여기서 처음 드러났다.

### 4-2. ⑥⑦⑧ 첫 가동으로 확정된 판정 (2026-07-29, 0.5.4b)

| 발견 | 판정 | 반영 |
|---|---|---|
| 유니크 재배(cultivated) 카드에 **베이스타입 줄이 없음** — 파서가 모드 조각(`"(100"`)을 베이스로 잡아 48건 오염 | 동명 일반판에서 **승계** | `uniques_page.parse_page`/`process` |
| PoB 유니크 블록의 `Variant:`·`{variant:N}` 줄을 베이스로 잡은 것 6건 | 메타 줄 스킵 + **현재 변형의 베이스 선택**(없으면 마지막 선언분) | `uniques.parse_block` |
| 트리 `stats`에 위키 마크업 잔존 4,161건 | **제거**(3a) | `tree.normalize_stats` |
| 트리 `stats`의 `\n` 병합 350건 | **두 언어 합의로 분할**(3b, 아래) | `tree.normalize_stats` |
| stats 빈 어센던시 노터블 5건이 제외되며 실존 노드 13개가 트리에서 끊김 | 5건을 **구조 노드로 수록** | `tree.process_tree`의 `hub` |
| `Nebuloch`·`Nightfall`·`Prism Guardian`의 베이스타입이 PoB와 다름 | **poe2db 기준**(사람 판정) — KB는 이미 poe2db 값 | 데이터 변경 없음 |
| 유니크 획득 경로 커버리지 0% | **수집하지 않기로 확정** — 유니크는 고정 경로가 아니라 사냥 산물이라 KB에 담을 실익이 적다. 특정 보스 한정분은 필요해지면 재검토 | ⑧ 리포트의 유니크 0%는 결함이 아님 |
| `Attribute` 소형 노드 293개가 "힘·민첩·지능을 각각 +5"로 읽힘 | 실제로는 **셋 중 택1**(사람 판정) → 선택지를 stats에서 빼고 **구조 필드로 승격** | `data.attribute_choice = {value, options}` |
| 그 외 내부 stat id 32줄 (`focus decay delay ms 5000`, `carried_spectral_bell` …) | **보존**(사람 판정) — 노드 고유의 조건·한계치일 수 있어, 지우면 예상 못 한 리스크를 안은 빌드나 성립하지 않는 조건이 나온다 | 손대지 않음 |

**`attribute_choice` 승격의 근거**: 삭제만 하면 오답("셋 다 부여")은 없어지지만 **선택지 자체가 사라진다**.
이 노드는 아이템 착용·스킬 사용 요구치를 맞추거나 스탯 스태킹을 하려고 **능동적으로 골라 찍는** 노드라
(사용자 지적), 생성기가 "무엇을 고를지" 결정하려면 기계가 읽을 수 있어야 한다 — 조건 1급 필드(RC1).
`passive.schema.json`이 `additionalProperties: true`라 스키마 변경 없이 들어간다.
**제거 규칙은 이 패턴에만 좁혀 적용한다** — 내부 stat id처럼 보인다고 일괄 삭제하지 않는다.

### 4-3. 모드 획득 판정 — 양 소스 교차가 필수인 이유 (2026-07-30 확정)

**PoB 스폰 가중치만으로 모드의 획득 가능성을 판정할 수 없다** (사용자 지적으로 확정):
PoE2에서 PoB의 weightVal이 성기게 채워져 있어, 가중치 0인 모드에 에센스·완벽한
에센스(Alloy)·브리치·훼손 등으로 **실제 획득 가능한 모드가 섞여 있다**.

- **교차 축**: poe2db 클래스 페이지(`/us/<class>#ModifiersCalc`)의 임베디드 JSON —
  획득 경로별 풀(normal·corrupted·desecrated·essence·perfect_essence·breach_*·
  chronomancy/berserking/… )과 DropChance(진짜 가중치)가 통째로 실려 있다.
- **매칭**: 계단식 — (접사명,패밀리,ilvl) 키 → (패밀리,ilvl) → 정규화 텍스트(결합 포함).
  Alloy 계열은 poe2db Name이 접사명이 아니라 부여 화폐 링크(이름 매칭 원천 불가),
  하이브리드는 PoB 두 줄 ↔ poe2db 한 줄.
- **판정 결과 (0.5.4b, 승인 2026-07-30)**: 보류 867 중 **185 승격**(poe2db 확인,
  poe2db:<pool> 획득 경로 부착) · **682 제외 + 원장 기록**(양 소스 모두 획득 경로 없음).
  원장(`unobtainable_mods`)은 매 패치 재검증 — 카탈로그에 다시 나타나면 부활 후보 리포트.
- **E-2 재판정**: "베이스에 없는 태그로만 스폰" 155건은 삭제가 아니라 **실존 풀**
  (chronomancy·berserking·decay·soul·marksman·destruction — poe2db 확인)이었다.
  삭제 판정을 철회하고 poe2db:<pool> 경로를 부착했다. 검증기의 태그-어휘 교차는
  "spawn_weights 축"만 보므로 별도 경로 풀을 죽은 태그로 오인할 수 있다 — ⑥ 해석 주의.
- **Desecrated 249종**: PoB에 아예 없는 신규 모드군(equipment 198·jewel 32·waystone 19)
  → poe2db 단독 소스로 신규 수록 (SUPPORTED_INFERENCE).

**3b 분할 규칙 — 왜 "두 언어의 합의"인가**: poe2db의 `\n`은 **효과 경계**일 때도 있고
(`Avatar of Fire`: "…Converted to Fire Damage\n Deal no Non-Fire Damage") **단순 줄바꿈**일 때도 있다
(`Crystalline Resistance`: "…if you have at\n least 5 Red…"). 어느 소스도 단독 정답이 아니다 —
**PoB도 같은 자리를 잘못 쪼갠다**. 그래서 en/ko 항목 수가 일치할 때만 분할하고 아니면 접는다.
측정: (A) en을 PoB 줄로 대체 → en/ko 어긋남 590건 + Unseen Path 197줄·직업 조건부 95줄 **소실** ·
(B) 무조건 분할 → 문장 반토막 · **(C) 채택안 → 어긋남 0(구조적 보장)**.

## 4-1. 구현 판정 게이트 (KI-8)

**원칙: 존재를 기본값으로 두고 반증을 찾지 않는다 — 구현의 양성 증거가 있어야 KB에 들어간다** (반프록시를 데이터 존재 판정에 적용).

3개 독립 신호(전부 기계 판정): **A**=poe2db `From` 카드 비어있지 않음(획득 경로) · **L**=목록 멤버십(fetch-plan 포함) · **P**=PoB 덤프 존재.

| A | P | 판정 | 처리 |
|---|---|---|---|
| ✓ | ✓ | 구현됨 | KB 수록 |
| ✗ | ✗ | 유령(PoE1 잔재, 예: Bane) | 자동 제외 — 리포트에 근거와 함께 명시(조용한 삭제 금지) |
| ✓ | ✗ | 구현됐으나 PoB 미지원 | 개별 판단 — 수록 + "PoB 계산 불가" 플래그 후보 |
| ✗ | ✓ | PoB 잔재 or 획득 파싱 실패 | 개별 판단 |

- **제외 원장**: 승인된 제외는 `knowledge/ingest/exclusions.json`(정본 커밋)에 기록 → 다음 패치에 재심사 불요. 매 패치 재검증에서 획득 증거가 새로 생기면 **"부활 후보"**로 리포트에 표시.
- 검증 실증(2026-07-29, 0.5.4b): Bane = 목록 미포함 ∧ PoB 부재 ∧ From 카드 부재 — 3신호 전부 음성. 정상 젬(Ancestral Cry) = `From /1`.

**한계 명시**: 위는 *카탈로그 완전성*(엔티티 전수)의 기준이다. *서술·메커니즘 지식의 완전성*("모든 상호작용을 안다")은 원리적으로 종결 불가능한 열린 집합 → 완전성 선언 대상이 아니라 학습 루프(인사이트 누적)로 계속 자라는 것으로 취급한다.

## 5. 증거 체인 (계보)

```
knowledge/ 커밋 (본 repo)
  └─ ingest manifest: { patch, 데이터repo commit 해시, PoB commit, 도구 버전 }
       └─ poe2-ai-wiki-data <patch>/ (원시 그 자체)
```

"이 값 어디서 왔지?" → 본 repo 커밋에서 기계적으로 원시까지 역추적. **어느 PC에도 유일본이 없다** — 진실은 항상 두 repo(push된 상태)에 있다.

## 6-1. 실행 주체 분리 (KI-7) — 저비용 에이전트 운용 설계

토큰 대량 소모 우려에 대한 답: **파이프라인 대부분은 LLM이 아니라 코드가 실행한다** (AD-3의 ingest 적용).

| 단계 | 실행 주체 | 토큰 |
|---|---|---|
| ① fetch · ② parse · ④ merge · ⑤ validate · 리포트 생성 | **순수 Python CLI** — 에이전트는 실행·감독만 | ~0 |
| ③ match 예외 판단 | 자동 매칭=코드, 실패 소량만 LLM | 소량 |
| ⑥ 승인 | 사람 | 0 |
| ⑧ 서술 재작성 | **저성능 모델 투입 지점** (아래) | 대량이나 통제됨 |

**저성능 에이전트(저티어 Claude/Codex)가 안전한 이유 — 4중 장치:**
1. **멱등 CLI + 체크포인트**(KI-4): 중복 실행·중단 모두 무해.
2. **코드 가드레일**: 스키마 검증이 쓰레기 거부, append-only, 정본 진입은 ⑥게이트 뒤에만 — 약한 모델이 정본을 오염시킬 경로가 없음.
3. **`skills/kb-ingest/` 스킬**: 번호 매긴 정확한 명령 절차(재량 제거). 약한 모델일수록 레일 위에서만 달리게.
4. **LLM 개입 지점의 구조화 계약**: ③⑧의 입출력을 스키마로 고정(자유 산문 금지), 위반은 코드가 반려 — 품질 편차를 검증기가 흡수.

**서술 재작성(⑧)의 저모델 운용:** 대상=큐레이션 엔티티 수백뿐(벌크는 서술 없음) · 엔티티당 독립 작업(병렬·분담·재시도 자연) · 입력 고정(poewiki 원문+검증된 구조 레코드만으로 재작성 → 환각 여지 조임) · **산출물 기본 라벨 = `UNVERIFIED`**(신뢰는 모델 성능이 아니라 라벨 체계가 관리, 스팟체크로 승격) · 상위 모델은 스팟체크·충돌 판정에만.

**순서 함의:** 수집 시작 전에 ingest CLI(fetch/parse 골격)와 스키마가 코드로 존재해야 한다 — "코드 먼저, 수집은 그 다음"(로드맵 반영).

## 6-2. 지식 획득 확장 순서 (확정, 2026-07-29)

젬 파이프라인 완주로 기계(fetch·체크포인트·판정 게이트·원장)가 검증됐으므로, 이후 카테고리는 **같은 기계에 파서만 추가**하며 아래 순서로 확장한다:

```
① 젬 merge (진행 중 — 첫 실 KB 커밋)
② 패시브 트리 (PoB TreeData 덤프 — 쉬움, P4 트리 최적화 대비)
③ 유니크 아이템
④ 베이스 아이템 + 모드 풀 (제작규칙 RC4 설계 동반 — Modifier 스키마 상세화 필요)
⑤ 서술 트랙 가동 (KI-2, poe2wiki 재작성 — KI-7 §6-1) ← **가동 (2026-07-30)**: 수집기·wiki 게이트(`narrative fetch|check`) + 35건 완성.
   **서술 라벨 승격 규칙 (사용자 확정 2026-07-30 — 사람 전수 검증은 비현실적)**:
   `UNVERIFIED` →(모델 스팟체크: 원문 revid·구조 레코드 대조, 별도 패스)→ `SUPPORTED_INFERENCE`
   →(대화·플레이에서 인게임 확인 시 **건별 즉시**)→ `IN_GAME` →(패치노트 근거)→ `CONFIRMED_OFFICIAL`.
   모순 발견 시 `CONTRADICTED`(경고 노출). 승격은 front-matter `verified_by` 필수 — 게이트가 강제.
   '판단 노트' 섹션은 우리 추론 층이라 검증 대상 외 (그래서 상한이 SUPPORTED_INFERENCE).
⑥ 화폐·룬·웨이스톤·콘텐츠 (P3~P4 필요 시점에)
   └ 예외: **제작 화폐 259종은 ④로 앞당겨 수록** (2026-07-30 사용자 지적·승인 —
     모드 획득 경로가 화폐를 가리키는데 화폐 레코드가 없었다. 제작규칙과 한 몸)
```

순서 변경은 사용자 협의 후에만.
