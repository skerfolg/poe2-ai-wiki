# 기존 설계·구성·근거 형식 감사 — R2 입력

2026-10-30, R1 F-1 실행 중 읽기 전용 조사.
범위는 동결된 구현의 형식·책임 관측이며, R1 결과 해석이나 목표 스키마 확정이 아니다.
정책: [BLUEPRINT](BLUEPRINT.md). UI 쪽 관측: [소비 계약 감사](POK_UI_CONTRACT_AUDIT.md).

## 기존에 있는 것

| 소유자/형식 | 확인한 계약 | 재설계에서 보존할 가치 |
| --- | --- | --- |
| `artifacts/design.py`의 DesignDoc/parse_design | 한국어 헤더4종, 확정/잠정/미검증, 큐/관문, 수식/표를 관대한 Markdown 파싱으로 추출 | 기존 문서 가져오기와 미지 원문 보존, 가설의 claim/proof, 누락 경고 |
| `pob/buildxml.py`의 BuildSpec/spec_from_dict | 실제 계산에 필요한 클래스·전직·레벨·노드·젬·장비·주얼·config·선택 능력치. 계산 외 메타데이터는 명시한 별도 허용 키로 구분 | 계산 입력과 설계 판단을 분리하고 모르는 키의 조용한 소실 방지 |
| `engine/provenance.py` | 구성 축과 상세 문맥의 서명·설명·낡음 진단, 자신의 산출 축을 문맥과 구분 | 단일 전체 해시만 비교하지 않는 변경 이유와 근거 유효 범위 |
| `engine/optimization_readiness.py` | optimization_contract, 실제 비교 범위/입력에 연결한 receipt, 추천 준비도/차단 | 같은 후보·변경 대상·관측 축의 근거 재사용과 범위 확인 |
| `engine/assemble.py` | 실제 계산한 구성과 저장 스펙 정합, spec.json/build.xml/build.pob/validation.json와 manifest 저장 | 재계산 가능한 실물과 원본, 검증·측정 결과의 계보 |
| `artifacts/tool_results.py` | 전체 입력/결과/출처의 불변 해시·참조·페이지 회수 | 설계 문서에 숫자를 재전사하는 대신 원측정과 연결할 기반 |
| `artifacts/store.py` | 날짜+slug의 독립 build_id, 파일 내용 해시와 기록 | 기존 사용자 산출물을 보존하는 이행과 별도 논리 설계 ID/리비전 매핑 검토 |

## 비어 있거나 다른 뜻인 것

- DesignDoc의 확정/잠정/미검증은 판단·검증 분류다. 사용자 고정/메커니즘 필수/잠정 구현/성능 후보의
  역할 구분과 같지 않다. 역할·채택 상태·근거 상태를 한 필드로 합치면 조건부 필수를 표현하기 어렵다.
- 기존 parser 설명의 '더 스키마화하지 않는다'는 이전 정책이다. 새 청사진이 우선하지만
  이전 Markdown을 조용히 무효로 만들거나 임의의 확정 앵커로 승격하지 않는 이행이 필요하다.
- 안정적인 설계 항목 ID, 요구 조건과 특정 공급자의 구분, 대체/의존/변경 영향은
  현재 DesignDoc의 문자열 목록에서 자동으로 보장되지 않는다.
- 문서의 가설 판정 조건은 좋은 기반이지만 실제 측정·인게임 관측·구성 리비전의 연결과는 별개다.
  파싱 성공을 메커니즘 성립이나 추천 품질 인증으로 사용하면 안 된다.
- 현재 독립 build_id는 기록물 식별자다. UI의 논리 buildId/revision과 자동으로 같다고 가정하지 않는다.
  새 산출물·기존 설계의 개정·불변 측정의 각 식별 관계를 R2에서 명시해야 한다.
- `artifacts/anchors/`는 출처가 있는 외부 PoB 레퍼런스다. 트리 연결의 target anchors와
  이번 설계의 필수 조건 앵커도 서로 다른 개념이다. 같은 단어라는 이유로 같은 저장소/ID로 합치지 않는다.

## R2가 결정할 것

1. 기존 문서/스펙/근거 중 각 정보의 정본과 파생 표현, 가져오기·렌더·재개 규약.
2. 앵커 역할, 조건/공급자/대체/의존, 검증 질문과 근거 상태를 표현할 최소 계약.
3. 문서·실물 구성·측정·UI 편집 리비전의 연결과 충돌/부분 적용/복구 의미.
4. 기존 receipt/도구 결과 참조를 재사용할 범위와 추천 준비도·성립성·품질 판단의 분리.
5. 어느 누락/변경 영향을 결정적으로 감지할 수 있고 어떤 판단은 AI/사용자에게 남겨야 하는가.

이는 R1 관측과 함께 검토할 질문이다. 특정 데이터베이스·새 모듈·저장 경로·상태 기계를
이미 채택했다는 뜻이 아니다. 동결 코드에는 변경을 가하지 않았다.

## 후속 읽기 전용 확인 — 이행 시 잃으면 안 되는 정보

2026-10-31 추가 비교 A/O-1 진행 중 확인했다. 아래는 현재 필드의 의미이며
R2 계약 채택이나 R3 구현 완료를 뜻하지 않는다. 참가자 코드와 입력은 변경하지 않았다.

| 관측 | 실제 코드/계약 | R2에 필요한 구분과 시험 |
| --- | --- | --- |
| 파싱 결과는 문서 원본이 아니다 | `artifacts/design.py`의 `DesignDoc`과 `parse_design` 반환은 추출된 헤더·목록·수식·표다. 전체 원문/미지 문단을 담는 필드는 없다 | 기존 문서 가져오기는 원본 바이트/해시를 별도로 보존해야 한다. 추출 필드만 렌더한 문서를 무손실 복원이라고 부르면 안 된다. 미지 헤더·문단·주석을 포함한 왕복 fixture가 필요하다 |
| 복원 표식은 계산 외 메타데이터지만 동작에 영향을 준다 | `pob/buildxml.py`의 `_SPEC_ONLY_KEYS`는 derived_from/restored_from/optimization_contract를 허용한다. `engine/autofill.py::unstamped_rares`는 restored_from이 참이면 희귀 자동 채움 대상에서 제외한다 | 계산용 필드가 아니라고 삭제하면 제공된 빌드의 처리 의미가 달라진다. 반대로 이 문자열 자체를 검증된 출처나 성립성 증명으로 승격하면 안 된다. 복원→명시적 변경→계산의 입력 보존과 근거 재검토를 함께 시험해야 한다 |
| 기존 문맥 서명과 불변 측정 식별은 같은 것이 아니다 | `engine/provenance.py::derivation_context`는 축별 문맥/설명을 만들고 `_digest`는 잘린 SHA1 표기를 쓴다. 실행 receipt에는 별도 SHA256 계산이 있다 | 문맥 차이 설명은 재사용하되, 짧은 문맥 서명 하나를 전체 구성/원본 XML의 강한 동일성 증명으로 사용하지 않는다. 실제 측정 입력·구성·표현 리비전의 소유와 전체 해시 범위를 명시해야 한다 |
| UI 편집 리비전은 별도 소비 계약이다 | `pok-ui/src/shared/contracts.ts`의 BuildDocument는 id/revision/xml/originalXml/undo, Calculation은 revision/at/result/restoreNotes를 갖는다. AgentRequest도 현재 id/revision/xml을 전달한다 | 논리 설계 ID/리비전을 기존 UI 숫자 revision이나 PoK 날짜+slug build_id와 암묵적으로 같게 만들지 않는다. 늦은 계산 결과·제안 적용·undo에서 어떤 원본과 설계 리비전이 대응하는지 명시해야 한다 |

기존 `tests/unit/test_design.py`는 목록/표 추출과 누락 경고의 계약을 보여준다.
이 테스트의 존재나 과거 통과가 원문 무손실 이행을 증명하지는 않는다.
이번 작업은 읽기 전용 확인이며 새 테스트를 실행하거나 위 이행 요구를 구현하지 않았다.

이 관측을 바탕으로 [소유·저장 후보](POK_REDESIGN_RECORD_OPTIONS.md)를 준비했다.
서버가 현재 헤드를 소유하는 방식과 호출자 작업 공간/체크포인트 방식을 비교하며,
어느 쪽도 채택하거나 저장 경계를 변경하지 않았다. 초기 기록·공급자 대체·분기·원자적
설계/실물 적용·원문 복귀 예제로 R2에서 계약을 결정할 입력이다.
